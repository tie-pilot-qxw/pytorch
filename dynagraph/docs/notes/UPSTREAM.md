# Upstream comparison: Elias Ellison's CUDA graph runtime checkpoint (2026-09-14) vs DynaGraph

Written 2026-09-19. Motivation: the PyTorch Conference agenda item "Parametrized Dynamic Shape CUDA Graphs" (Elias Ellison, Meta;
Daniel Galvez, NVIDIA), and galv's PR #160351 / #182691 ("Parameterized cuda graph launch"). The PR itself only does
**pointer** parametrization (it still records one graph per shape, `shape_cache[int_key]`); what actually does "one graph across shapes" is the
branch `cudagraph-runtime-checkpoint-2026-09-14` on the eellison fork (commit 53c39d6, directory `cudagraph_checkpoint/`: README, STATUS,
manifest, sources.tar.gz). To check the evidence below, download that directory from GitHub and unpack `sources.tar.gz`.

How it was read: six readers each read one area (dynamic-parameters, native-runtime, architecture-docs, compiler-handoffs,
landing-and-benchmarks, allocation-and-user-kernels) with the same set of 7 questions, and then one merger wrote what follows, setting it against our summary.
**Note**: the native-runtime reader's answer was truncated; for that area the merger additionally read the RESULTS/status files, and the C++ was not checked file by file.

In one sentence: **they achieved "one graph across concrete shapes", but the shape class is very narrow (1-2 integer inputs, rank <= 2, only Grid1D with a single
xnumel allowed), extern is excluded by construction, there is no path for topology changes, there are zero benchmarks, and it is only validated on CUDA 13 / GB300.** We can no longer say
"upstream only has pointer parametrization"; the differences have to be stated row by row, as in the table below.

One sentence per area:
- dynamic-parameters (cudagraph_inductor_frontend_comparison/compiler_dynamic_parameters + compiler_dynamic_user_handoff) (39 files): The two areas implement and GPU-verify (2+2 tests, M=13 capture then M=2/7/35/36 hits) a single captured graph replayed across dynamic batch by evaluating a compiler-emitted integer program in C++ and host-patching grid/scalar/pointer bytes with cuGraphExecKernelNodeSetParams before cudaGraphLaunch, with all buffers allocated per replay from the eager caching allocator; scope is Inductor pointwise/1D-grid Triton (+ one user wrap_triton call), no extern/cuBLAS/custom ops, no topology change, no training, no benchmarks.
- native-runtime (35 files): The checkpoint really does replay ONE captured cudaGraphExec across different sizes (widths 2/7/35/36 after a width-13 warm-up) by host-side C++ cuGraphExecKernelNodeSetParams patching of grid dims, i32/i64 scalars and pointers from a compiler-emitted integer recipe, with all buffers allocated per replay from the eager caching allocator and outputs wrapped as fresh tensors; but it is Triton-pointwise-only (no extern/cuBLAS/collectives, no topology change handling, 1-2 symbolic ints, rank<=2 contiguous), backward-only on a toy 4-kernel module, 44 GPU tests total, and carries no performance, memory, or real-model numbers.
- architecture-docs (8 files): These seven docs (aliases: CCH/=cudagraph_inductor_frontend_comparison/compiler_cute_handoff/, NC/=CCH/multiple_calls/backward_contract/automatic_origin/attachment_candidate/native_candidate/) describe a host-side C++ 'numeric replay' of ONE captured graph across varying boxed integer extents (symbolic V4 IntExpr layouts/scalars/grids evaluated per hit, kernel-node params rewritten before cudaGraphLaunch, allocations served per replay from the caching allocator with an optional saved-input drop/claim path), restricted to Inductor-generated Triton (Grid1D), user Triton (retained-IR only) and one two-operand CuTe DSL kernel with contiguous rank-1/2 symbolic buffers; cuBLAS/cuDNN/extern/aten/collectives, topology change, TMA, unbacked shapes and autotuning are not addressed; every file is self-declared source-only, no benchmark numbers exist, the only test count is 'CPU192 passed' for the static release with GPU qualification 'still in progress', and dynamic release plus symbolic end-to-end runs are explicitly not yet executed.
- compiler-handoffs (40 files): The compiler-handoff increments implement and GPU-test true single-graph cross-shape replay (capture at batch 13, native C++ replay at batches 2/7/35/36 with zero Python frames, symbolic grids/scalars/allocations from Inductor call records) but only for pure-Triton ComputedBuffer programs with 1-2 boxed symbols, one user Triton kernel and no extern/GEMM/backward/TMA/autotune coverage, with no benchmark numbers and no explicit node-update CUDA API named in this area.
- landing-and-benchmarks (64 files): This checkpoint does implement and GPU-test one captured CUDA graph replayed across many batch sizes without recapture (compile-time symbolic records: boxed integer inputs -> IntExpr for xnumel, grid ceildiv and buffer sizes, bound to a C++ boxed replay with the capture pool retired and fresh outputs per call), but only for straight-line Inductor Triton pointwise/persistent-reduction graphs of rank <=2 with 1-2 integer inputs, Grid1D, no extern/cuBLAS/custom ops, no TMA, no unbacked shapes, inference-only in these files; the sole performance number is host submission ~33 us vs ~82 us eager on a synthetic 20-kernel chain, with no device-time, memory, cudagraph-trees or model-level results, and partitioning, allocator planning, closed operators and automatic tree installation explicitly deferred.
- allocation-and-user-kernels (59 files): The area implements host-side C++ per-node re-parametrization (cuGraphExecKernelNodeSetParams patching pointers, int32/int64 scalars and gridDim; block/shared fixed) so one captured graph per host-branch arm replays across widths, with intermediates/outputs allocated per replay from the eager caching allocator and the capture pool retired; coverage is limited to fp32 Grid1D Inductor pointwise/reduction kernels, one user-Triton pointwise test, and a narrow CuTe single-launch subset, with cuBLAS/cuDNN/extern kernels, collectives, topology changes, unbacked shapes, TMA and in-graph autotuning all explicitly rejected or absent, and no performance numbers.

## 2. What upstream has and we do not (with evidence)

1. **Structured records emitted by the compiler instead of parsing the wrapper source**: `WrapperCallRecords` V4 / `IntExpr` / `_cudagraph_grid_recipe` are attached directly to the launcher by Inductor codegen (`wrapper.py: collect_cudagraph_call_records`). We recover the formulas by reading the generated source.
2. **Byte-by-byte check at preparation time**: every captured pointer/scalar/grid byte is verified against its compiler source ("Captured grid differs from its symbolic recipe or supported domain", `cudagraph_boxed_replay.py`).
3. **Per-step allocation from the eager allocator + backward saved-input release schedule**: storage is released after its last use and reused by an output slot, with three controls release/disabled/retain_graph (`output_slots/RESULTS.md`). We use a fixed arena + headroom; implications for peak memory [inferred: upstream is closer to eager's memory profile, but upstream itself states it has no peak-memory data].
4. **TTIR parameter-analysis admission for user Triton kernels** (pointer read/write/alignment facts, whitelist) and the **CuTe DSL mixed pipeline**.
5. **Robustness of parameter replacement**: in-place / aligned / misaligned (offset-one) Parameter replacement; misaligned goes through a `copy_if_misaligned` prologue (`compiler_dynamic_parameters/RESULTS.md`).
6. **Multi-variant native dispatch**: `PythonBoxedGraphDispatch` uses an `int8_t(*)(int64_t*, double*)` predicate on the boxed integers to select a variant, and calls back only on a miss (native-runtime area Q1).
7. **Compile-cache round trip**: local FX cache miss/save->hit/load restores the native entry (`cudagraph_latest_qualification.json: status`).
8. **Public API**: `CUDAGraph.update_kernel_params(dict[node][arg]=bytes)`, `_cuda_get_capture_frontier`, `keep_graph=True` + `instantiate()`.
9. **Audit discipline**: every qualification has a manifest sha256, root and independent audits, and failed attempts are retained.

## 3. What we have and upstream does not (only what the findings support)

1. **Extern kernels (cuBLAS/cuDNN/aten fallback/NCCL) and topology changes**: upstream excludes them by construction and has no path at all for topology changes; we have per-shape child-graph swap-in, full-graph selection, and SWITCH conditional nodes. This is currently the hardest difference.
2. **Device-side update path**: upstream only has host-side `cuGraphExecKernelNodeSetParams`.
3. **Arena with zero per-step allocation, and a host path that overlaps with the previous step**: upstream allocates all buffers in C++ on every replay.
4. **Full training step (forward+backward) and multi-GPU**: upstream has only one generated 4-kernel backward, the forward still goes through ordinary Inductor, and there are no collectives.
5. **Random ops, in-place/mutated inputs**: upstream rejects `effectful_ops`/`mutated_inputs` outright.
6. **Measured numbers**: upstream has zero benchmarks.
7. **Wider shape class**: upstream is limited to 1-2 integer inputs, rank<=2 contiguous, Grid1D with a single `xnumel`, and literal reduction ranges; we already serve conv/GEMM models [inferred: implies coverage of higher rank and non-Grid1D].
8. **Runtime numeric check against eager** (first N shapes): upstream only compares outputs in tests.
9. **"badly written code" sweep** (15/18): upstream has no corresponding workload.

## 4. Uncertainties about upstream

1. **The native-runtime reader's answer was truncated** (Q1 breaks off midway at the `CUDAGraphParams.cpp update_replay` evidence), and Q2-Q7 are missing; my conclusions about that area's backward/release/cache come from additionally reading `output_slots/RESULTS.md`, `cudagraph_current.md` and `cudagraph_latest_qualification.json`, and source_delta was not checked file by file.
2. **Cross-shape correctness relies only on output comparison**: the audit itself states "no per-hit ABI snapshot is claimed"; width is fixed at 128, and the test batches never change the divisibility of `xnumel` by 16, so divisibility specialization was never tested across shapes (reader observation).
3. **Test counts are non-additive and overlap each other** (252/44, 280/11, 298/12, 211/23, 154/18...); no single number can be used to represent coverage.
4. **Whether the `benchmark` directory ever produced timings**: the archive contains only non-timing artifacts; `cudagraph_status_archive/2026-09-14_before_dynamic_backward_qualification.md` ("Earlier checkpoints and benchmarks"), referenced by `cudagraph_current.md`, **is not in this archive**, so numbers elsewhere cannot be ruled out.
5. **"1,931 source files" is not the size of the prototype**: `cudagraph_input_reclamation/.../review1/source/` is a snapshot of the entire PyTorch source tree (the grep hits for `unbacked`/`ChildGraphNode` are all in these original upstream files); the prototype's own code is far smaller than that [inferred].
6. **Whether the CuTe path counts as "one graph across shapes"**: the 4 guard variants show that each shape class is prepared separately, ~25 s each; one can only say there is reuse within a guard class.
7. **Portability**: only validated on CUDA 13 / GB300 aarch64; preparation requires CUDA>=12.8 + `cuda.bindings`, ParamInfo requires >=12.4; there is no evidence about behavior on H100/CUDA 12.x.
8. **Progress after 09-14 is unknown**: the checkpoint states its next steps as "broaden representative workloads" and "smaller reviewable integration"; this archive does not contain later commits.

## 5. Recommendations

1. **Rewrite the novelty argument**. Drop "upstream only has pointer parameterization"; replace it with a verifiable difference matrix: extern/topology (child-graph swap-in + SWITCH), device-side update, zero-allocation arena, full training step + multi-GPU, measured numbers. For each item, attach the location of upstream's corresponding rejection code (the list of `return None` conditions in `wrapper.py: collect_cudagraph_call_records`) as counter-evidence.
2. **Run upstream's workloads as-is on our machines and report numbers**: `sin(x*weight)` M=13->2/7/35/36; 20-kernel pointwise (13,17)->(7,11)/(11,7)/(2,511)/(2,513); rmsnorm (13,1024)->2/7/35/36 rows; 4-kernel backward width 13->2/7/35/36. Upstream has zero timings for these, so we can produce the first quantitative comparison (mind the 550 W power cap and the high host load; interleave configurations as described in [docs/METHODOLOGY.md](../METHODOLOGY.md)).
3. **Borrow two upstream mechanisms to make the planner more robust**: (a) have Inductor codegen attach structured records directly (IntExpr + grid recipe) instead of parsing the wrapper source; this directly serves the "badly written code" axis; (b) at preparation time, verify the captured bytes once against the symbolic formulas; this is cheap and moves the current "check the first N shapes against eager" forward to capture time.
4. **Answer the peak-memory question**: upstream explicitly leaves it open, and we have no numbers for the peak cost of our arena+headroom on backward either. Measure the peak memory of the conv/GEMM models vs cudagraph trees vs eager; if the gap is large, consider an optional early release of saved activations on the backward side (upstream has a schedule design to refer to).
5. **Keep watching two upstream roadmap items**: item 12, "closed ops escape hatch" (graph break/partition or re-record), and item 10, "split the captured graph into cached child graphs"; once either lands, it will erode our differentiation on extern/topology. At the same time we need to prepare an answer on user Triton/CuTe, for which the summary currently contains nothing we can claim.
