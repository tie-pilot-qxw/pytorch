## Glossary (read this first)

### opaque kernel

A kernel that **the compiler can neither see into nor modify**.

| | Transparent kernel | Opaque kernel |
|---|---|---|
| Example | Triton kernels generated by Inductor | Precompiled kernels from cuBLAS, cuDNN, FlashAttention |
| Source | Generated by our own codegen | Only a binary inside a `.so` |
| Parameter layout | Defined by us; we know what every byte is | Unknown |
| Can it be changed to "read the shape from device memory"? | Yes, by changing a few lines of Triton | **No** |

Why this is critical for this project: the core technique is "have the kernel read shapes and pointers from device memory instead of baking them into the graph". For a transparent kernel that is a one-line change; for an opaque kernel you can only patch the graph node's parameters from the outside (but you need to know the parameter layout), or replace the kernel entirely.

Measured result: attention, as an opaque kernel, is benign (always 4 kernels, only the grid changes); cuBLAS is nasty (it switches kernel function whenever M changes, and **the kernel function is exactly the one thing in a graph node that cannot be changed from the device side**).

### The four sources of shapes

Illustrated with a piece of code:

```python
def forward(self, x):              # x: [B, L, H]   <- class 1
    h = self.norm(x)               # [B, L, H]      <- class 2
    scores = q @ k.transpose(-1,-2)  # [B, heads, L, L]  <- class 2
    keep = (scores > 0).nonzero()  # [?, 2]         <- class 3; ? is known only to the GPU
    y = gather(h, keep)            # [?, H]         <- class 3
```

**Class 1 - input shapes of the compiled region** -- `B`, `L`, `H`.
How does the host decide them? **We don't care.** They are just a few integers, written each step into a fixed-address device buffer (InputContext). Host-side work = writing a dozen or so ints.

**Class 2 - pure functions of the input shapes** -- `h` is `[B,L,H]`, `scores` is `[B,heads,L,L]`, some workspace is `B*L*4H*2` bytes. All of them are algebraic expressions in B/L/H.
**Inductor already stores these expressions internally in sympy** (ShapeEnv). So the planner kernel just evaluates these expressions on the GPU -- mechanical codegen; this covers the vast majority of intermediates.

**Class 3 - data-dependent sizes inside the region** -- how many rows `keep` has.
This number is computed by the `nonzero` kernel itself and written to device memory. **If the host wants to know it, it has to synchronize**, and that synchronization is exactly what we are trying to eliminate. The planner kernel can simply read it from that device memory. Today, when PyTorch hits this class, it just turns cudagraph off.

**Class 4 - host code inside the loop** -- see below. This is the only one that genuinely cannot be handled automatically.

### "Host code inside the loop"

A CUDA graph can only contain GPU operations. **Any CPU code in between cuts the graph** -- launch the first half of the graph -> run the CPU code -> launch the second half.

```python
for step in range(n_steps):
    nbr = build_neighbor_list(pos)   # <- host code (often a C++ extension), and the returned "number of neighbor pairs" comes back to the CPU
    energy = model(pos, nbr)         # <- GPU work; this part can be compiled + captured
    pos = integrate(pos, energy)     #   one time step of molecular dynamics
```

The key point is **where** it sits:

- **Outside the compiled region** (like above): **harmless**. It only produces inputs; the input shapes come in as a few integers, i.e. class 1. That is how torch.compile is used today, and the same holds for us.
- **Inside the loop you want to put into the graph**: this is the real problem. For example, you want to turn the whole MD time-step loop into one graph (only then can the per-step launch overhead be eliminated completely), but the neighbor-list rebuild is Python/C++ and cannot be moved in.
- **Inside forward**: the nastiest kind.

```python
def forward(self, x):
    idx = (x > 0).nonzero()
    n = idx.shape[0]          # <- this line forces a GPU->CPU sync
    buf = torch.empty(n, ...) # <- the host must know n before it can allocate
```
To allocate `buf` the host must know `n`, so it syncs, and so the graph breaks here. This is the boundary between class 3 and class 4, and it is what **difficulty 1 (unbacked SymInt)** has to solve: keep `n` symbolic all the way through, never letting it come back to the CPU.

**Other common class 4 examples**: vLLM's scheduler (decides which requests run next, builds the block table), GNN neighbor sampling, dataloader collate, Python control flow such as `if loss.item() > thresh:`.

### "Host code inside forward" -- measured version

**Key clarification: the author wrote pure PyTorch, not a single line of CPU code. The host work is injected by PyTorch itself.**

Three things always happen on the CPU, and all of them need concrete sizes:

1. **Memory allocation** -- the CUDA caching allocator behind `torch.empty(n)` runs on the CPU and needs `n` to allocate
2. **Computing the launch configuration** -- `grid = ceil(n/128)`; the CPU computes the grid before the launch
3. **Any Python branch** -- `if n > 0:` needs the actual value

Normally these three are invisible because the sizes are known at compile time. **Only when a size is determined by data on the GPU do they surface: PyTorch has to copy that number from device memory back to the CPU, i.e. a synchronization.**

Measured (`../../microbench/dds_probe.py`, detected directly with `torch.cuda.set_sync_debug_mode("error")`):

| Pattern in forward | Under eager | torch.compile + reduce-overhead |
|---|---|---|
| `x[x > 0]` masked select | **forced sync** | `cudagraph_partitions=4` |
| `nonzero()` + gather | **forced sync** | `cudagraph_partitions=4` |
| `torch.unique` | **forced sync** | `cudagraph_partitions=4` |
| `torch.bincount` | **forced sync** | `cudagraph_partitions=4` |
| Control flow after `int(tensor)` | **forced sync** | `cudagraph_partitions=4` |
| [Control] `x * 2 + 1` | no sync | not partitioned, one complete graph |

Two things worth noting:

- **Dynamo has no graph break** (`graph_count=1`, `graph_break_count=0`). With `capture_dynamic_output_shape_ops` enabled it can keep the size as an unbacked SymInt without going back to the CPU. PyTorch already does this part fairly well
- **But the CUDA graph layer cannot hold up: it cuts the graph into 4 pieces.** A two-line function is cut into 4 pieces; in a real model with many such ops, the graph gets badly fragmented

This is the same disease as vLLM's piecewise mode, except that it happens inside Inductor, at a finer granularity, and silently.

> **A ready-made instrument for the P0 survey**: `torch._dynamo.utils.counters["inductor"]["cudagraph_partitions"]`. Run 188 models and count how many pieces each one is cut into -- that is the Figure 1 nobody has, and it requires no changes to PyTorch.

## TL;DR

**Goal (clarified): any messy model gets CUDA graphs just by running `torch.compile` on it.** Not squeezing a few more percent out of LLM training.

All mechanisms pass in measurement. **Two target workloads, sharing the same mechanism:**

| Target | How bad it is today | One-line benefit |
|---|---|---|
| **A. LLM serving** (the strongest motivation) | vLLM uses **piecewise cudagraph**, cutting the graph at attention; it captures **67 graphs** by batch size; Kimi-K2 DP32 with `--cuda-graph-max-bs 128` has the graphs eating **~20 GB/rank**, leaving only ~19 GB for KV cache; startup capture takes **36-65 seconds** | **One graph instead of 67**, attention is no longer cut out, and the saved memory turns directly into KV cache -> throughput |
| **B. Non-LLM dynamic models** (GNN / MD / point cloud / recommendation) | PyG officially recommends **just turning CUDA graph off**; PyTorch **simply disables cudagraph** on data-dependent output sizes; every field hand-writes its own pad-to-max | **From 0 benefit to some benefit** |

> **Warning:** the pessimistic conclusions of v1-v5 of this document **anchored on the wrong yardstick**: I used LLM training as the evaluation benchmark, and that is exactly the one field with no shortage of hand-written optimization. After switching the yardstick to "any dynamic model", all three problems once considered fatal dissolve; see Section 7.

Net findings from four rounds of measurement:

1. **The kernel set of attention is constant** (variable-length fwd+bwd is always 4 kernels; only the grid and the contents of cu_seqlens change). vLLM excludes attention from cudagraph on the grounds of "compatibility with all attention backends", not because the kernels themselves cannot be captured -- **this shows piecewise can be eliminated**
2. **cuBLAS's variant explosion is wave quantization**, not dozens of algorithms; in non-LLM workloads no large GEMM dominates, so this problem largely disappears
3. **Host-side patching can overlap with GPU execution** -- but only when the host *knows* the shape. **With data-dependent shapes the host must do a D2H sync, and that sync is exactly what we are trying to eliminate.** This is the hard reason the device side cannot be replaced
4. **Today PyTorch simply turns CUDA graph off on data-dependent output sizes** (`unique` / `nonzero` / variable-length `scatter` / `bincount` / `x[x>0]`), or splits the graph into fragments

## 1. Motivation: why serving and "messy open-source models"

Both points Xinwei raised hold up on checking, and the numbers are ugly.

### The very existence of piecewise cudagraph is the evidence

vLLM v1's official design doc:

> "In **PIECEWISE** mode, vLLM splits the computation graph **at attention or other cudagraph-incompatible operations**, capturing cudagraphs only for the submodules that can handle dynamic shapes."
> "Initial piecewise compilation was built to allow piecewise cudagraph capture, **excluding cudagraph-unsupported operations (mainly attention)**. This allowed *some* speedup from cudagraphs while maintaining compatibility with all attention backends."

In other words: **a production-grade inference engine deliberately gives up cudagraph at attention**, and every attention is a graph boundary. If this problem were already solved, piecewise would not need to exist.

What I measured today: FA2 varlen fwd+bwd under 10 very different (batch, length distribution) settings is **always 4 kernels**; only the grid and the contents of cu_seqlens change. Both are things a planner kernel can handle. The real reason vLLM excludes attention is that **host-side scheduling metadata** (num_splits, scheduler metadata) gets baked into the graph, not that the kernels cannot be captured -- FlashInfer's plan/run has already shown that putting the metadata on the GPU side makes it capturable. **Move the plan itself into the graph, and piecewise has no reason to exist.**

### Memory and startup cost of capture

| Phenomenon | Number | Source |
|---|---|---|
| Kimi-K2-Thinking FP8, DP32/EP32/TP32, `--cuda-graph-max-bs 128` | **cudagraph eats ~20 GB/rank, leaving only ~19 GB for KV cache** | sglang#24453 |
| GLM-5.2, 78-layer MoE, 42 shapes | graph memory **+2.4 GB** | LMSYS SGLang blog |
| vLLM captures 67 graphs by default | startup **>10 seconds** | vLLM docs |
| Qwen3-14B | capture **36-48 seconds**, one user reported **65 seconds** | vllm#16716 |
| Capture time grows linearly with the number of batch-size buckets | 3 buckets 0.33 s -> 60 buckets 1.8 s | LMSYS |
| When the batch has 6 requests | it uses the batch-size-8 graph and **pads 2 dummy requests** | SGLang |

People have already written papers specifically about this:
- **Foundry** (arXiv 2604.06664): *Template-Based CUDA Graph Context Materialization for Fast LLM Serving Cold Start*, cuts capture from ~54 seconds to ~7 seconds
- **Breaking the Ice** (arXiv 2606.07362): analyzes vLLM cold start and concludes **"CUDA graph capture remains the dominant bottleneck during initialization"**
- vLLM RFC #20098: Lazy CUDA Graph capture

> **Note Foundry's positioning**: it makes capturing N graphs faster. Our direction is to make **N = 1**, eliminating the problem at the root. Foundry's existence shows the problem is worth a paper, and at the same time it has not taken our spot.

### Why this motivation is much stronger than training

1. **Memory converts directly into throughput.** In serving, graph memory and KV cache share the same budget. Saving 20 GB is not "saving a bit of memory"; it means doubling the KV cache, which means throughput. This is far more compelling than "saving 3 ms of launch overhead"
2. **Padding is real waste.** With a batch of 6 padded to 8, every decode step computes dummies
3. **Cold start is a real pain point.** In serverless / elastic scale-out scenarios a 36-65 second startup is fatal; two papers are already going after it
4. **Piecewise boundaries have a real cost.** Every attention is one graph exit and re-entry; dozens of layers means dozens of them

## 3. Opaque kernels: GEMM is the real problem, attention is not

### cuBLAS's dozens of variants are not dozens of algorithms

After decoding the tile sizes from the nvjet kernel names: 103 values of M use 36 kernels, but there are only **5 BMs** (64/128/192/256/320), versus **19 BNs** (8/16/32/56/64/96/112/128/136/144/152/160/176/184/192/200/208/224/240). BN is the knob being turned, and the goal is to make the CTA count an integer multiple of the 132 SMs:

| M | Tile chosen by cuBLAS | CTA count | waves = CTA/132 |
|---|---|---|---|
| 768 | 128x192 | 132 | 1.00 |
| 1111 | 192x192 | 132 | 1.00 |
| 1536 | 128x192 | 264 | 2.00 |
| 2304 | 192x192 | 264 | 2.00 |
| 6784 | 192x192 | 792 | 6.00 |
| 8064 | 192x192 | 924 | 7.00 |

Overall: **70 of the 103 shapes land with "the last wave completely full or >75% full"**, whereas a random tile choice would give only about 25%. So the odd BNs such as 136/152/184/200 are wave-quantization knobs.

> **This is actually evidence in favor of persistent kernels.** Variant explosion is a symptom of *non*-persistent kernels: the grid is determined by the shape, so the tile has to be tuned to line up with the SM count. A persistent kernel with a fixed grid does not have this problem by construction; all that remains is load imbalance at the tail of the tile loop, which StreamK can smooth out.

### Can we handle cuBLAS directly? No, but we don't need to

Three reasons it can't, ordered by hardness:

1. **The kernel function changes.** Device-side update of a graph node can only change parameters, grid, and enable/disable; **it cannot change the kernel function itself**. When M changes, cuBLAS switches kernels, which is immediately out of bounds.
2. **The parameter blob is opaque.** Besides M, the nvjet parameter struct contains values precomputed for the tile scheduler. Reverse-engineering it takes capture-twice-diff followed by fitting, and it breaks as soon as NVIDIA upgrades.
3. **The TMA tensormap is frozen at capture time.** The most insidious one; see the hazard below.

Why we don't need to:

| Config | Relative to cuBLAS | Notes |
|---|---|---|
| Single fixed config (128x256) | 74-84% | At M >= 1024 already 86-95%; the gap is concentrated at M <= 777, where a fixed BN cannot fill the 132 SMs |
| Best of 5 configs (BN in 32/64/128/256) | About 95% | The winning BN changes with M: M=128 wants BN=32, M=1024 wants BN=256 |

**These 5 configs need no device-side dispatch mechanism at all.** The GEMM config depends only on M, and the host knows L before the launch, so the host picks one of 3-5 pre-instantiated templates, O(1).

### What already exists in the ecosystem

- **CUTLASS**: the problem shapes of grouped/ptr-array GEMM live in device memory; it has device-side tensormap update (`tensormap.replace`), async TMA descriptor update, and ragged contiguous grouped GEMM (example 92)
- **DeepGEMM**: the reason masked grouped GEMM exists is, in its own words, "when CUDA graph is enabled in the decode phase, the CPU does not know how many tokens each expert receives"
- **FlashInfer**: two-phase plan/run, the persistent kernel grid is fixed after compilation, plan metadata is cached on the GPU side, explicitly cudagraph-compatible
- **FA4** (2026-03, Blackwell) is written in Python with CuTe-DSL, so it is **modifiable**, unlike cuBLAS

> **Warning - Hazard**: DeepGEMM issue #444 -- during graph capture the TMA tensormap from the first run is recorded; on replay the distribution has changed, TMA uses the stale descriptor and reads out of bounds, giving an illegal memory access outright. **Dynamic shapes + TMA require updating the tensormap on the device**, and getting it wrong is silent.

### Attention: always 4 kernels

10 completely different (batch, length distribution) settings, total tokens 538-15013, max_seqlen 85-10905:

| Phase | Kernel count | What they are |
|---|---|---|
| forward | **1** | `flash_fwd_kernel`; all 10 settings hit the same one |
| backward | **3** | `dot_do_o` -> `dq_dk_dv_loop_seqk_parallel` -> `convert_dq` |

headdim (64/128/256) and causal do switch kernels, but they are constant within a training run. For comparison, sweeping 9 seqlens with torch SDPA: flash uses 6 distinct kernels, cuDNN 4, mem-efficient 3.

The only remaining variables are: the **grid** (changed via `SetGridDim`), the **contents of cu_seqlens** (already a device tensor), and **num_splits** (basically 1 in training).

> **Warning:** the existing FA3 cudagraph wrapper freezes the *contents* of cu_seqlens, the batch size, the total token count and max_seqlen together for the lifetime of the graph, because host-side heuristics are baked in. **Capturable != re-parameterizable.**

## 4. Incremental updates: the three-tier mechanism + the biggest risk

### Adding branches to an already-instantiated SWITCH: does not work

Empty slots are free at runtime (size 2->32 all cost 13-19 us), but after instantiate, putting a kernel into an empty body and then calling `ExecUpdate` fails outright with a topology-change error. Adding nodes fails the same way.

### But the kernel function itself can be swapped

In the CUDA header, `cudaGraphExecUpdateErrorFunctionChanged` is annotated "CUDA driver < 11.2", meaning that swapping the function is supported from 11.2 on. Confirmed by measurement. The three tiers:

| What changes | Mechanism | Cost | Needs instantiate? |
|---|---|---|---|
| address/extent/grid (changes every step) | planner kernel modifies them device-side, inside the graph | 0.05 us/node | No, zero host involvement |
| kernel function | host `ExecKernelNodeSetParams` / `ExecUpdate` | 0.73 / 0.47 us/node | No |
| topology (number of kernels changes) | re-capture from scratch + instantiate + upload | 19.8 ms for 3000 nodes | Yes, and it requires a fresh capture |

> Warning: a graph that contains device-updatable nodes **can be instantiated only once**. When the topology changes, it is not "re-instantiate" but "re-capture from scratch". Preparing 5 templates means capturing 5 times.

### Good news: the premise can be relaxed to "convergence"

The graph does not have to stay fixed forever; it is enough that **the mutation rate goes to 0 as the step count grows**. If a run hits 50 new topologies in its first 1000 steps and none afterward, that is 50 x 20 ms ~ 1 second.

This is easier to measure than the original claim: it moves from "a static classification of variability" to **"a dynamic convergence curve of variability"**. The control group already exists: cudagraph trees re-record for every new shape and never converge.

### Bad news: doing the same thing on the host may be enough

| What was measured | Result |
|---|---|
| A 3000-node graph that takes 63 ms to execute on the GPU; the host patches every node | **3.4 ms** (1.12 us/node) |
| Patching this graph **while it is running** | **All legal, non-blocking**, fits entirely inside the execution window |
| Does the in-flight launch get modified? | **No**, only subsequent launches are affected |
| A plain graph without device-updatable nodes | Can be instantiated twice -> **double buffering** is also possible |

So "host O(#nodes) vs device O(#symbols)" has to be discounted. As long as the GPU step time is clearly longer than the patch time, the host side is sufficient and simpler. An implementation that extends galv's PR #182691 from "patch pointers only" to "also patch shape and grid" would very likely get nearly the same steady-state performance on standard variable-length SFT.

**What the device side still has going for it, ranked by strength:**

1. **Values the host does not know at all** (the only qualitative difference). Per-expert token counts in MoE, packing/sorting done on the GPU, sequences assembled on the device in RL, speculative-decoding accept lengths. For the host to patch these it needs a D2H sync, and once that sync happens the scheme falls apart.
2. **Many launches per step**. Gradient accumulation with 16 micro-batches, PP with many micro-batches: every launch has to be re-patched beforehand. When a single micro-batch takes only a few ms of GPU time, 3.4 ms cannot be hidden.
3. **The host is already busy**. Dataloader, Python loops, multi-rank jitter. And on the PyTorch side the path goes through Python, so 1.12 us/node becomes several times worse.
4. Absolute work: 0.15 ms of GPU vs 3.4 ms of CPU, 20x less, and spent on the side that has slack.

## 5. System design

```
HOST per step O(#symbols)            GRAPH one launch, byte-for-byte unchanged
+--------------------+
| write InputContext |--+    +--------------------+
| L, B, cu_seqlens   |  +--->| planner kernel     |
| input/label ptrs   |       | sizes/strides      |--+-> patch node params + gridDim
| pinned -> 1 memcpy |       | = f(L)             |  +-> write RuntimeContext table
+--------------------+       | 3000 nodes 0.15ms  |  +-> set SWITCH conditions
                             +--------------------+
                                       |
                    K1 -> K2 -> ... -> K3000 (fwd + bwd)
                    kernel function / topology / dependencies all fixed
```

**Four kinds of variability:**

| What changes | Mechanism | Status |
|---|---|---|
| address | planner `SetParam` (the Inductor kernel layout is known) / kernel reads from ctx | Measured |
| extent (numel/stride/grid) | planner `SetParam` + `SetGridDim`. smem is constexpr, so it is fixed anyway | Measured |
| algorithm | attention is a constant 4 kernels, nothing to handle; only GEMM remains, the host picks a template by M | GEMM only |
| code (new kernel) | see the three-tier fallback in section 3 | Design |

**Memory: v1 does not need a planner with dynamic layout.** One arena; Inductor's existing memory planning (including lifetime reuse) computes the offsets at L_max, and all shapes reuse them. Transformer activations are monotone in the token count, so the plan is automatically valid for smaller L. The arena capacity has to be the max_shape peak_live anyway, the same as the peak of actually running one L_max step. Only v2 needs dynamic offsets (slot allocation for PP with many micro-batches, VMM on-demand backing).

**Training semantics:**
- RNG: philox (seed, offset) can be read from the device; the planner advances the offset according to the shape (the consumption is a function of L, known at compile time)
- fwd/bwd: AOTAutograd's two graphs each become one immutable graph, sharing the arena; saved activations live in fixed slots
- Distributed: DDP/FSDP collectives act on parameter gradients, whose shapes are static and can be captured directly; TP/SP/EP activation collectives depend on L, and v1 uses a max-size bucket for them
- Debugging: with an immutable graph + device state, errors show up as silent garbage results; a verify mode that cross-checks results is needed from week one

## 6. The ceiling: look at two kinds of workload separately

Measured: serial nodes inside a graph cost about **0.78 us/node**, vs about 2-4 us/node for eager launches. So the upper bound on how much a graph can improve launch overhead is **3-5x**. The key question is whether that 3-5x is worth anything, and that **depends entirely on the workload**:

| Workload | Share of launch overhead | What the 3-5x is worth |
|---|---|---|
| LLM training (3000 nodes, 200 ms step) | GPU-bound, launch is mostly hidden | **Very little**, a few percent. This is what I computed earlier, and it is where I anchored wrong |
| GNN / MD / point cloud / recommendation | kernels are small and memory-bound, **the GPU is badly underutilized**, launch overhead dominates | **A lot**, it can be a large chunk of wall-clock |

PyG's official guidance states directly: **"CUDA Graphs should be disabled for neighbor-sampled GNN training"**, because the mini-batch size changes every time and repeated recording does not pay off. In other words, these workloads today get **none of the graph benefit at all**.

> The only way to get below 0.78 us/node itself is to reduce the node count (extreme fusion / megakernel). But for the second kind of workload above, **just getting the 3-5x is already a big win**, because today they get 0x.

## 7. Novelty: why "automation" is a real gap

### First, correcting myself: the earlier kill list was anchored to the wrong yardstick

In the first round I listed a pile of "someone has already done this" and concluded there was no novelty. The problem with that judgment: **every item I listed was hand-written for one model family, and almost all of them were written for LLMs.**

| What I earlier said was "taken" | What it actually is |
|---|---|
| Megatron Core's MoE ECHO (sync-free dropless MoE training) | **Hand-built by NVIDIA for its own MoE layer**. Switch to another model and it is gone |
| FlashInfer plan/run | **Hand-written one kernel at a time** |
| DeepGEMM masked grouped GEMM | Same, hand-written for MoE decode |
| Megatron's packed-sequence CUDA graph | The approach is to **pad cu_seqlens to a fixed size and fall back to eager when it overflows** |

LLM training is the one workload in the world with hundreds of engineers hand-writing kernels full-time. Using it as evidence that "this problem is solved" is like saying "someone has hand-written assembly, so we do not need compilers".

### The real evidence: every dynamic-workload field has independently invented the same hack

| Field | What they do | Source |
|---|---|---|
| Molecular dynamics (TorchMD-Net) | Implemented a "static shape mode" that **creates placeholder neighbor pairs to pad up to a preset maximum**, then makes the architecture ignore the placeholders' contributions | TorchMD-Net 2.0 |
| 3D sparse convolution / point cloud (TorchSparse) | **Pads GEMM operands with zeros** to group small GEMMs and reduce launch overhead | TorchSparse |
| LLM variable-length training (Megatron) | **Pads cu_seqlens to a fixed size**, falls back to eager when it overflows | Megatron Core |
| GNN (PyG) | Official advice is to **just turn off CUDA graphs** | PyG guide |

Four unrelated fields each hand-wrote the same workaround: **pad to max + mask**. This kind of independent, repeated invention is itself the standard signal of "a missing layer of abstraction".

### And PyTorch today simply gives up on this

- **data-dependent output sizes disable CUDA graphs outright**: `torch.unique()`, `torch.unique_consecutive()`, variable-length `scatter`/`gather`, `torch.bincount()`, `x[x > 0]`. Turning on IR-level partitioning only **breaks the graph into fragments**; it does not solve the problem
- PyTorch's own DevLog (2026-07): trying to trace a whole TorchTitan DeepSeek-V3 MoE step into one FX graph, the unbacked SymInt batch/seq dims made **every layer either silently specialize to a concrete integer or raise a data-dependent error outright**. It took 11 fixes to barely get it running
- A closed bug: `pytorch#172728 - Unbacked SymInt leaks into cudagraph-safe partitions` (from vLLM, labels `module: vllm` / `vllm-compile`)

### So what is the contribution

> **Automatically compile any PyTorch program with dynamic shapes (including data-dependent output sizes) into a form that can execute as a CUDA graph: no padding, no per-shape recapture, and nothing for the user to write.**

Four supporting points:

0. **The serving-side problem is widely acknowledged as unsolved.** vLLM still uses piecewise capture (cutting the graph at attention); capture memory can eat 20 GB/rank, cold start takes 36-65 seconds, and there are already two papers (Foundry, Breaking the Ice) attacking this. They all optimize under the premise of "N graphs"; nobody has tried turning N into 1
1. **Nobody has automated it.** All sync-free schemes are hand-written, and hand-writing only happens for LLMs
2. **The host-side approach does not hold here at all.** The rebuttal from section 4 that "host patching can overlap" only works when the host *knows* the shape. The neighbor count in a GNN, the number of active voxels in sparse convolution, the output length of `nonzero` -- these are computed by the kernels themselves; for the host to know them it needs a D2H sync, and that sync is exactly what we want to eliminate. **The planner kernel just reads them from device memory; the host cannot do that.** This is a qualitative difference, not a few percent of speedup
3. **These workloads get 0 CUDA graph benefit today**, not "80% is already there and we add 5%"

### Which of today's measurements still count

| Measurement | Does it still count under the new framing? |
|---|---|
| device-side node update takes effect in the same launch, 0.05 us/node | Yes: the core mechanism, fully counts |
| the 0.78 us/node graph floor | Yes, but must be reinterpreted per section 6 |
| three-tier fallback (device patch / host function swap / re-capture) | Yes, counts |
| a device-updatable graph can be instantiated only once | Yes, an important limitation |
| host patching can overlap with the GPU | Partly: holds only when the host knows the shape; does not hold for the target workloads |
| cuBLAS 61 variants / wave quantization | No: LLM-specific; large GEMMs do not dominate the target workloads |
| attention is a constant 4 kernels | No: most target workloads have no attention |

**I spent a whole day on cuBLAS and attention, and those two happen to be LLM-specific problems, basically irrelevant to the new framing.**

## 8. List of hard problems (ranked by hardness)

### 0. First, a very favorable gap: today nobody knows what the cudagraph coverage is

PyTorch issue #124506, verbatim: **"there is a lack of visibility into how much of a torch.compiled model has been cudagraphed since the system silently falls back when encountering limitations."** The only way to find out is to grep the logs. Users are asking for either a hard-fail switch or a coverage report.

So **Figure 1 is ready-made, cheap, and something nobody has**: run the 188 models from the PyTorch 2 paper and measure "what fraction is really fully cudagraphed, how many pieces it is broken into, how many recaptures happen per step". This number is very likely ugly, and precisely because the fallback is silent, the community itself does not know it.

### 1. Plumbing unbacked SymInt all the way through Inductor to graph nodes <- the real technical core

Today, as soon as `torch.unique` / `nonzero` / variable-length `scatter` / `bincount` / `x[x>0]` shows up, cudagraph is **disabled outright**, or the graph is broken into fragments. PyTorch itself only in 2026-07 made 11 fixes in order to trace one MoE; see bug #172728 (unbacked SymInt leaking into a cudagraph-safe partition, **fixed and closed**).

Good news: this can build on their ShapeEnv work, and **nobody has really done the CUDA graph part**.

### 2. Device-side memory planning when sizes have no static upper bound

When a data-dependent size has no upper bound, a max-shape arena is either impossible or hugely wasteful. CUDA graphs do have memory alloc/free nodes, but **their sizes are fixed at capture time**, so they cannot help. What is needed: one arena + a planner kernel doing sub-allocation on the device + a bail-out when the arena is exceeded. This has been promoted from "optional in v2" in the original plan to core.

### 3. The host-side planner problem (needs re-framing)

**Concern:** we do not know how the planner on the CPU does its planning, so we cannot move it to the GPU.

**Re-framing: we do not need to know how it plans; we only need its decisions to reach the graph as "data" rather than as "structure".**

| Where the shape comes from | Can it be handled automatically? | How |
|---|---|---|
| the **input** shapes of the compiled region | Yes, no need to know how the host computed them | the host writes a dozen or so integers into InputContext, and that is all |
| **pure functions** of the input shapes (the vast majority of intermediates) | Yes | they are sympy expressions in Inductor's ShapeEnv; mechanically codegen them into the planner kernel |
| data-dependent ops **inside** the region | Yes | the size is written to device memory by some kernel; the planner reads it directly |
| **host code inside the loop we want to put into the graph** (neighbor list rebuild in MD, the vLLM scheduler, collate) | No | this is the real hard part |

**Key clarification: the fourth category is not caused by our design; it exists today too, and it is orthogonal.** Today torch.compile + cudagraph likewise require the host to compute the input shapes before it can launch. We do not make it worse, and we are not responsible for fixing it.

Three honest options for the fourth category:

- **(a) Do not cross it.** Draw the graph boundary at the host code and get "one graph per compiled region", the same as torch.compile today. **This is the default, and it loses nothing.**
- **(b) Lookahead / pipelining**: while the GPU runs step N, the host computes the plan for step N+1. Standard practice, but **it only holds when step N+1's plan does not depend on step N's GPU output**. Dataloader prefetch: holds; an autoregressive scheduler: does not.
- **(c) Pull the host code into the graph.** Only works when it is traceable. numpy / C++ extensions cannot come in.

**On the "fake lookahead plan"**: the cleaner formulation is **speculate the structure class + verify with a device-side guard + fall back on a miss**. Not guessing the concrete size, but guessing "which structure class this step belongs to". The device guard can use SWITCH (measured 11 us/point, perfectly acceptable at the start of a step). The paper would measure the miss rate, which ties in nicely with the "convergence curve" claim.

**On having an agent rewrite code**: agreed that it cannot be the approach -- requiring users to set up a token before they can use `torch.compile` would ruin the contribution. The legitimate weak version is to use an agent **during offline development** to generate device planners for non-traceable host code, then verify them against the original code with differential testing. That is a tool, not a user requirement. The claim must be "the 188 models run without changing a single line"; the agent can only be mentioned in passing as an optional escape hatch.

### 4. Silent fallback: both motivation and infrastructure we need ourselves

Whatever cannot be covered quietly falls back, without reporting an error. This means (a) the Figure 1 from item 0 is there to be made; (b) **we must first build coverage observability for ourselves**, otherwise we cannot tell whether our own system really runs end-to-end or is also silently degrading.

### 5. Correctness under an immutable graph

RNG offset advancement, autograd, collectives, mutation/aliasing. Errors are **silent garbage results**, not crashes. A verify mode that cross-checks step by step is needed from week one.

### 6. opaque kernel (mostly solved, and LLM-specific)

The cuBLAS variant explosion is wave quantization (section 3), and attention is a constant 4 kernels. Both are light in the target workloads.

## After section 8: fake run -- needed, but no need to patch the driver

**Idea**: we cannot see inside opaque kernels, and we do not know how the host will compute the grid / pick the kernel. So run it once first and record what it did.

**The idea is right, and it is exactly the analysis pass this compiler should have. But the implementation does not need LD_PRELOAD to hook `cuLaunchKernel`** -- we are going to capture anyway, so after capture we just read the nodes back out, all with public APIs:

| What we want to know | What to read it with | Measured result |
|---|---|---|
| which kernel it is | `cuGraphKernelNodeGetParams` + `cuFuncGetName` | Yes: read `nvjet_sm90_hsh_256x128_64x4_1x2_h_bz_coopA_NNT` |
| grid / block / smem | same as above | Yes: `grid=(2,64,1) block=(384,1,1) smem=213188` |
| topology (how many nodes, of what type) | `cuGraphGetNodes` + `cuGraphNodeGetType` | Yes |
| parameter layout (which byte is what) | `cuFuncGetParamInfo` | Partly: cuBLAS reports only **1 parameter, a big 1784-byte blob**, with no breakdown into fields |
| parameter values | the node's `extra` (cuBLAS goes through `CU_LAUNCH_PARAM_BUFFER_POINTER`; `kernelParams` is NULL) | Yes: the bytes can be captured, but they carry no semantics |

So the output of a fake run is **not a formula but a classification**: assign each launch site to the tier of mechanism it needs. This lines up exactly with the three tiers in section 4.

### Measured: the same GEMM, what changes when M changes

(`../../microbench/fakerun_probe2.cu`, `[Mx4096] @ [4096x4096]` fp16)

| | M=1024 | M=1088 | M=4096 |
|---|---|---|---|
| kernel | `256x128_..._coopA_NNT` | **`192x192_..._coopB_NNN`** | `256x128_..._coopA_NNT` |
| grid | (2, 64, 1) | (2, 66, 1) | (2, 66, 1) |
| **smem** | 213188 | **188604** | 213188 |
| **topology** | 1 Kernel | 1 Kernel | **MemAlloc -> Memset -> Kernel -> MemFree** |

**M moved by only 64 rows and both the kernel and the smem changed; at M=4096, cuBLAS inserted its own workspace alloc/zero/free nodes, and the topology changed.**

Compare with what a graph can modify:

| Field | Modifiable device-side? | Modifiable host-side? |
|---|---|---|
| parameter values | Yes, `cudaGraphKernelNodeSetParam` | Yes |
| gridDim | Yes, `cudaGraphKernelNodeSetGridDim` | Yes |
| enable/disable | Yes, `cudaGraphKernelNodeSetEnabled` | Yes |
| **kernel function** | No | Yes, `ExecKernelNodeSetParams` (0.73 us/node) |
| **sharedMemBytes** | No | Yes (same as above, but there is no corresponding device-side API) |
| **topology** | No | No, only re-capture from scratch (19.8 ms for 3000 nodes) |

-> **cuBLAS hits all three, and no device-side mechanism can rescue it.** This is the final evidence that it "must be replaced with a device-parameterized GEMM".
-> Conversely, **smem changes can be absorbed by "pre-placing several variant nodes + SetEnabled"**, because each pre-placed node carries its own smem. This is the unique value of SetEnabled over SetParam.

### Does the grid need a fake run? Two cases

- **Triton kernels generated by Inductor: no.** Inductor already writes the grid as `cdiv(xnumel, XBLOCK)`, and `xnumel` is a sympy expression. This is the second category (a pure function of the input shapes); the planner kernel just computes it the same way. **This is the vast majority of kernels.**
- **opaque kernels (cuBLAS/cuDNN/custom extensions): yes.** The formula lives inside the library and can only be observed. But what gets observed is often "the kernel changed too", which goes straight to tier 3, and then the grid is no longer the main point.

### The two kinds of branches really do need different mechanisms

| What the branch depends on | Example | When it is known | Mechanism | Cost |
|---|---|---|---|---|
| **Values known to the host** (input shapes) | `if seq_len > 512: use_flash()` | before launch | the host picks one of several pre-instantiated graph templates | **O(1), zero runtime overhead** |
| **Values on the device** | `if n_selected > 0:`, MoE expert load, NMS survivor count | only the GPU knows | (1) predication (compute both sides, mask one out)<br>(2) SWITCH conditional node<br>(3) pre-placed nodes + SetEnabled | (1) wastes compute<br>(2) 11 us/point<br>(3) 0.85 us/slot, but must be pre-placed |

**Key: the first kind needs no device mechanism at all**, and no fake run to guess either -- the host knows, so it just picks the template. Only the second kind truly needs device-side control flow, and the second kind is exactly what host-side approaches cannot do at all (knowing the value would require a sync).

### The mandatory objection: "Why not just capture once and replay?"

This is the first thing any reviewer will ask. Two failure modes, measured (`../../microbench/replay_limits.py`):

**Mode 1 -- same shape, but the addresses changed.** At capture time `x=1, y=10`, and replay gives 11. Switch to two new tensors `x=100, y=1000` (new addresses) and replay: **still 11**. What is baked into the graph are the two pointers from the moment of capture; it cannot see the new tensors at all.

**Mode 2 -- the shape changed.** A graph recorded for n=64 has `numel` and `grid` baked in for 64; using it to compute n=256 only computes the first 64.

cudagraph trees today exist to patch exactly these two holes: copy the inputs into the fixed addresses from capture time (one copy per step), and record a new graph for every new shape. Measured cost:

| | Time |
|---|---|
| 40 different shapes, first run (compile + recording) | **3.43 s** (about 86 ms per shape) |
| the same 40 shapes, second run (all hits) | **49.8 ms** (about 1.2 ms per shape) |

Hit vs miss differ by **70x**. The problem with variable-length workloads is that the next shape is often a new one, so you keep paying 86 ms forever.

### So what does the fake run actually buy

**Key distinction: the fake run's K is for "distinguishing", not for "covering".**

| | What K is | How big K is |
|---|---|---|
| bucketing / capture-replay | how many shapes you want to cover | as large as the precision you want. vLLM: 67 graphs, 20 GB |
| **fake run** | enough to classify every launch site | **2-3 sets are enough, independent of the size of the shape space** |

After classification only **one** template comes out, covering a whole region of shape space, because the varying parts are supplied by the planner on the device. This is the same idea as galv's PR capturing twice to identify which bytes are pointers -- twice, not N times.

And **when things are data-dependent, capture-replay is not an option at all**: there is no way to know in advance which values the number of rows output by `nonzero` can take, so the shape space cannot be enumerated and therefore cannot be bucketed.

### Mandatory objection 2: "A fake run is also a capture, so why not just replay the graph that was just captured?"

**Because the fake run is not done every step; at runtime there is not a single capture.** When I said earlier "read the nodes after capture" I did not make the frequency clear, which makes it easy to think it happens every step.

| Phase | How many captures | What for |
|---|---|---|
| compile / warm-up | K = 2-3 **fake run captures** | only to **classify** launch sites (is the topology stable, does the kernel change, does smem change). These graphs are thrown away after use |
| compile / warm-up | **1 more**, an instrumented capture | all intermediate buffers come from the arena (fixed addresses), kernel nodes are marked device-updatable, and the planner is attached in front. **Only this one is the template that is kept** |
| runtime | **0** | only replay + the planner modifying parameters on the device |

**Key: the template is not any of the fake run graphs.** The fake run graphs are recorded with concrete shapes and are valid only for those shapes. The template is a separate recording whose parameters are symbolic.

If this were changed to "directly replay the graph that was just captured", that would be recording a graph per shape at runtime -- which is exactly cudagraph trees. The measured gap (`../../microbench/template_vs_recapture.py`, 20 chained Triton kernels, 200 steps, results cross-checked and identical):

| Input distribution | A: record a graph per new shape | B: single template + ctx | Gap |
|---|---|---|---|
| **a different shape every step** (variable-length workload) | 0.552 s, **200 graphs captured** | 0.011 s, **1** graph captured | **48.6x** |
| only 8 shapes (bucketable) | 0.015 s, 8 graphs captured | 0.007 s, 1 graph captured | 2.1x |

The two rows together are the whole story: **when shapes keep being new, A is forever recording; when there are only a few shapes, A finishes recording and then always hits, and B's advantage drops to 2x** (and part of that 2x is just the difference between a persistent grid and an exact grid).

> Note that this microbenchmark measures **the capture cost saved**, not end-to-end model speedup. In a real system each new shape also pays for Inductor compilation (measured earlier: 40 shapes 3.43 s, about 86 ms each), so the real gap can only be larger. But also be clear: if there are only a few shapes to begin with, the measured gap is the 2.1x row above, and capture-replay / bucketing already covers that case (see the boundary table below).

**One more point**: a fake run is only needed for opaque kernels. For the Triton kernels Inductor generates itself, the compiler already knows the parameter layout and the grid formula, so not a single fake run is needed. For a pure-Triton model K = 0.

### The honest boundary: when capture-replay is enough

| Scenario | Is it enough? |
|---|---|
| static shapes | **Enough**, just replay; this project is not needed |
| only a few shape values (3-8 buckets) | **Enough**, bucketing is entirely reasonable |
| many shapes, but bounded and enumerable | Barely; this is what vLLM looks like today: 67 graphs, 20 GB, 36-65 s startup |
| **unbounded / data-dependent shapes** | **Impossible**; this is this project's territory |

Stating this boundary clearly matters more than exaggerating the benefit -- otherwise it is over-engineering.

### So where the fake run sits in the pipeline

```
warm-up phase (run K different sets of inputs)
      |
      +- capture into a graph
      +- cuGraphGetNodes / cuGraphKernelNodeGetParams / cuFuncGetName
      +- classify each launch site:
             topology stable? --no--> tier 3: a separate template for this shape range
             kernel/smem stable? --no--> tier 2: swap the function on the host (or pre-placed variants + SetEnabled)
             only grid/params change? --> tier 1: planner modifies them on the device (0.05 us/node)
      |
      v
compile-time output: a set of templates + one planner kernel per template
```

**This machinery is also the implementation of the coverage census from item 0**: run the 188 models and count how many launch sites fall into tier 1 / 2 / 3. The fraction that falls into tier 1 is the fraction this system can absorb.

## What to do about opaque kernels (measured, not guessed)

This is the most critical question for the automated route: if every opaque kernel we hit makes the system degrade to cudagraph trees, then the system is useless for any model that uses cuBLAS/cuDNN/extensions.

### Measured: does the kernel sequence actually change when the shape changes

`../../microbench/opaque_stability2.py`. For each size, record separately the **sequence** of "which kernels this call launched", then compare whether the sequences differ across 6 sizes spanning 3 orders of magnitude.

| Op | Kernels per call | Distinct sequences across 6 sizes | Result |
|---|---|---|---|
| cumsum | 2 | 1 | **fully stable** |
| scatter_add | 1 | 1 | **fully stable** |
| index_select | 1 | 1 | **fully stable** |
| embedding_bag | 1 | 1 | **fully stable** |
| layer_norm | 1 | 1 | **fully stable** |
| softmax | 1 | 1 | **fully stable** |
| conv2d (batch varies, cuDNN) | 1 | 1 | **fully stable** |
| conv2d (H/W varies, cuDNN) | 1 | 1 | **fully stable** |
| sort | 2 or 7 | 2 | topology changes |
| topk | 2 or 20 | 2 | topology changes |
| unique | 3 or 12 | 2 | topology changes |
| nonzero | 3 or 4 | 2 | topology changes |
| GEMM (cuBLAS) | 1 | **5** | kernel changes |

**8/13 are fully stable.** That includes cuDNN convolution -- even changing H/W does not switch the kernel, which is good news for vision models.

### Three conclusions

**1. Most opaque kernels are tier 1 -- but the grid formula cannot come from fitting; it has to come from registration.**

> **Correction**: an earlier version of this document said "the hypothesis class for the grid is small; two or three observation points are enough to pin it down". **That is wrong**; measurement contradicted it, see below.

Measured grid as a function of n (`../../microbench/grid_recoverability.py`, 6 values of n spanning 256x):

| kernel | Measured grid | Fit result |
|---|---|---|
| scatter_add | 4, 8, 16, 64, 256, 1024 | `cdiv(n, 1024)` OK, clean |
| index_select | 4, 8, 16, 64, 256, 1024 | `cdiv(n, 1024)` OK |
| softmax | 4, 8, 16, 64, 256, 1024 | `cdiv(n, 1024)` OK |
| layer_norm | 32, 64, 128, 512, 2048, 8192 | `cdiv(n, 128)` OK |
| embedding_bag | 1024 x6 | constant (persistent style) OK |
| cumsum (2 kernels) | 1,1,1,1,2,5 / 3,5,9,35,137,547 | `cdiv(n, 209716)` / `cdiv(n, 1917)` **(suspect) these two constants are obviously forced to fit** |
| conv2d (cuDNN) | 128, 128, 128, 640, 2688, 10880 | FAIL: does not fit the hypothesis class (grid depends jointly on several dimensions) |
| GEMM (cuBLAS) | 4x2, 8x2, 8x4, 8x8, 8x12, 2x64 | FAIL: 2D grid, and the kernel itself also changes |

**The key is the two entries marked (suspect).** `209716` and `1917` are clearly not real constants (the true values are probably something like a tile count); they just happen to match at these 6 points. **Pick an n we have not probed and the fitted grid may be wrong, and a wrong grid for an opaque kernel = silently wrong results or out-of-bounds accesses.** This is the empirical evidence that "fitting is unreliable".

Also: **we cannot fall back on "just launch a somewhat bigger grid"** -- we do not know what the extra blocks of an opaque kernel will do; they may write garbage. This is completely different from the Triton kernels we generate ourselves.

**So the correct source of the grid is registration, not fitting.** And the burden of registration is much smaller than it sounds:

| Kernel source | Where the grid comes from | Who does the work |
|---|---|---|
| Inductor-generated Triton | The compiler already has the sympy expression `cdiv(xnumel, XBLOCK)` | **Nobody**. In a compiled model these are the vast majority of kernels |
| ATen fallback (sort/scatter/embedding_bag/...) | A built-in table, written once for the few dozen ops that are actually used | **Us, once**, not the user |
| cuBLAS / cuDNN | Same as above, or go straight to one of the two routes "replace it / break the graph" | Us |
| User-defined extensions | `torch.library.custom_op` **already requires today** registering a fake/meta function that declares the output shape; adding a grid declaration is an increment on an existing burden | The user, but it still runs without the declaration (see below) |

**Not registering does not break anything**: an opaque op with no grid declaration just breaks the graph at that point and degrades to today's piecewise. **The floor is "the same as the status quo".**

So what are those 2-3 fake runs still good for? **They do "observation", not "extrapolation"** -- they observe whether this op's kernel sequence is stable, whether the topology changes, and which parameter bytes move. These are facts we see directly; nothing has to be guessed. So:

- **fake run -> decide the tier (reliable, pure observation)**
- **registration table -> grid formula (reliable)**
- **fitting -> only usable as a cross-check; unreliable on its own**

**Identifying the parameter bytes, on the other hand, is reliable**: use an **adjacent-size diff** -- capture once at n=1000 and once at n=1001; the 4-byte field in the blob whose values differ by exactly 1 is n. And pointers do not need to be found at all: intermediate buffers all live in an arena at a fixed address, so the pointers never move.

**2. Ops like sort / topk / unique / nonzero have only two paths, not a continuum.**

Measured: each has exactly **2 sequences**: small inputs take a single pass (e.g. `sbtopk` / `radixSort`), large inputs take CUB multi-pass. So it is a **threshold**, not N shapes.

- Size known on the host -> the host picks between **2 templates**, O(1), zero overhead
- Size is data-dependent (`nonzero` is the typical case) -> use a 2-way device SWITCH, measured 11 us/point

**Two paths x a few such ops = a handful of templates, not one graph per shape.** This is the key to the whole problem being solvable.

**3. GEMM is the only real trouble spot, and it happens to have the best replacements.**

5 kernels (at K=N=512), and at larger K/N cuBLAS additionally inserts its own MemAlloc->Memset->MemFree workspace nodes (measured earlier in `fakerun_probe2`: M=1024 gives 1 node, M=4096 gives 4). Kernel, smem and topology all change.

Handling, in priority order:

| Approach | Cost | Applies to |
|---|---|---|
| Switch to a device-parameterized implementation (CUTLASS grouped / Triton persistent, M read from device memory) | Measured 74-84% of cuBLAS with a single config, ~95% with 5 configs | GEMM, attention -- exactly the two most important ones, which also happen to have mature replacements |
| Pin one cuBLASLt algo so it stops switching kernels | **Not measured**, worth doing first -- if pinning drops it to tier 1, no need to replace the implementation | All cuBLAS calls |
| Pre-place multiple variant nodes + planner `SetEnabled` | 0.85 us/slot; **can absorb smem changes** (each pre-placed node carries its own smem, which SetParam cannot do) | Number of variants <~ 13 |
| Swap the function on the host side (when M is known on the host) | 0.73 us/node, can overlap with the GPU | Training/inference cases where M comes from the input shape |
| Break the graph at that op (= vLLM piecewise) | Lose the gain for that segment | Fallback, **no worse than today** |

### Fallback principle

When we hit an opaque kernel we cannot handle at all (e.g. a custom extension that dispatches internally by size and whose variants cannot be enumerated), break the graph there. The result equals today's piecewise -- **the floor is "the same as the status quo", not "worse"**. This matters for a system that has to run 188 messy models: it guarantees there is no negative gain.

> **The census P0 has to be expanded into**: extend this 13-op table to every opaque op actually used by the 188 models, and count the distribution of tier 1 / 2-path / trouble spot. The tier 1 fraction sets the ceiling of this system.

## Closure check: is this mechanism enough to support the whole system

### The most critical premise, verified

**Under `dynamic=True`, one Inductor kernel covers all shapes.** Measured (`../../microbench/closure_check.py`): for a LayerNorm+Linear+GELU+Linear block, n=128 generates 8 cubins; after that, n = 129 / 333 / 1024 / 4097 / 16000 / 65537 -- **0 new ones**, across 512x.

This is the foundation of the whole tier-1 story: the vast majority of kernels the compiler produces are already shape-polymorphic; only the grid and the parameters change, and the planner can patch both.

### The cost of "asking", verified

`cublasLtMatmulAlgoGetHeuristic`, which does not launch and only asks "which one would you pick": **1.2-3.3 us per call**. Asking for all 100 GEMMs in a step is about 200 us, on the host, can overlap with the GPU, and after caching by shape class it is usually 0 calls. **Fully acceptable.**

(An unexpected number on the side: the host overhead of `torch.compile` per call for this small model is **368 us**, mostly Python and guards. For small models the bulk of the host cost is not kernel launches at all but Python -- which is actually one more argument for "full-graph capture".)

### What an unbacked SymInt is (what problem 1 is actually about)

torch.compile represents dynamic sizes with symbolic variables. There are two kinds of symbols, and the difference is **whether there is a concrete reference value (a hint)**.

**backed SymInt -- has a hint.** Comes from the shape of an input tensor:

```python
x = torch.randn(1024, 256)     # at trace time the hint for s0 = 1024
def f(x):
    if x.shape[0] > 512: ...    # the compiler answers "yes" using the hint, then records a guard: s0 > 512
```
The compiler **can ask questions about it**. After asking it records a guard; next time, if the shape does not satisfy the guard, it recompiles. So control flow works as usual.

**unbacked SymInt -- no hint.** Comes from data, not from shapes:

```python
u0 = x.nonzero().shape[0]       # at trace time there is no value at all; the data has not been computed yet
if u0 > 0: ...                  # cannot be answered -> DataDependentError (DDE)
```

The trouble is that **the compiler asks questions far more often than you would think**, and most of them are implicit:

| Implicit question | Where it shows up |
|---|---|
| Is this dimension 1 (can it broadcast)? | Almost every elementwise op |
| Is this stride combination contiguous? (requires comparing products of sizes) | Every layout decision |
| How many bytes does `torch.empty(u0)` need? | Every allocation |
| Is `u0 % 8 == 0`? | `view(-1, 8)`, vectorization |
| Is `u0 < 1024`? | Choosing a tile/block config |

Each one is a decision about an unknown. PyTorch has only three options: **raise a DDE**, **sync to get the real value** (which means specializing + breaking the graph), or **let the unknown propagate all the way down** -- and the last one requires every meta kernel, every stride computation, every allocation and every codegen path along the way to tolerate the unknown.

> PyTorch DevLog (2026-07) tried to trace an entire TorchTitan DeepSeek-V3 MoE step into one FX graph with batch/seq as unbacked: **"every layer either silently specializes to a concrete integer or raises a DDE outright"**; they fixed 11 places across ATen meta kernels / ProxyTensor / ShapeEnv / Inductor / collective bucketing / DTensor / FlexAttention.

**For us there is one more step**: even if Dynamo and Inductor keep it symbolic, it still has to survive all the way into **the kernel node's parameters** -- that is, the generated code must treat `u0` as "a runtime value read from device memory", not as a Python int on the host. Today Inductor's wrapper computes sizes in Python on the host. Bug #172728 is titled *unbacked SymInt leaks into cudagraph-safe partitions*.

**In one sentence**: problem 1 = can this symbolic unknown survive all the way from the trace into the graph node's parameters, without any link along the way demanding "give me a concrete number on the CPU".


### Important correction: what PyTorch wants is the **opposite direction** from ours

After reading issue #172728 (**closed**, from vLLM) and `should_partition` in main, I have to overturn something I said earlier:
I said "PyTorch itself is also fixing things in this direction, so we can build on their progress" -- **that is wrong**.

What the bug is about: with `graph_partition=True`, a custom op marked `cudagraph_unsafe` returned an unbacked symint `u0`,
and `u0` leaked into a partition that was supposed to be cudagraph-safe, producing code like this:

```python
extern_kernels.mm(reinterpret_tensor(arg2_1, (256 + ((-1)*u0), 512), (512, 1), 512*u0), ...)
```

A GEMM whose **shape and offset both depend on u0** sits in a partition that is going to be captured. Capture bakes these values in,
and the next time `u0` changes, replay computes wrong results or goes out of bounds.

**Their expected behavior: partitioning should isolate the data-dependent ops so that only fixed-shape ops remain in the capturable partitions.**

In other words -- **PyTorch's design premise is "the parameters of CUDA graph nodes are immutable constants, so anything data-dependent must be kept out".
What they built is a fence, and that bug is a hole in the fence. Our premise is "node parameters can be rewritten from the device on every launch",
so what we need to do is tear the fence down.**

This is not "they did half and we finish it"; these are two opposite directions.

**But for us this is actually good news**: they have already **precisely encoded** "which cases cannot go into a graph" in `should_partition`.
That list is our work list.

### The complete `should_partition` list (`torch/_inductor/scheduler.py:11166`)

The signature is `should_partition(node) -> str | None`; it returns the reason for splitting, or None. Item by item:

| # | Trigger condition | Returned reason string | Can we eliminate it |
|---|---|---|---|
| 1 | op is in `config.custom_should_partition_ops` | `custom partition op: {name}` | Explicitly specified by the user; respect it |
| 2 | `config.triton.cudagraphs` is off | `partition includes all ops when cudagraphs is disabled` | Not applicable |
| 3 | Non-GPU node | `{device} ops` | No (host ops have to be outside anyway) |
| 4 | `ir.DeviceCopy` | `DeviceCopy ops` | Partly (D2D yes; H2D needs a fixed staging buffer) |
| 5 | `ir.Switch` | `Switch ops` | **Yes** -- exactly what the CUDA conditional SWITCH node is for (measured 11 us/point) |
| 6 | Node has `unbacked_bindings` | **`unbacked binding ops`** | **This is the main battlefield** -- eliminated if the planner reads sizes from device memory |
| 7 | `is_cudagraph_unsafe_op(node)` | `CUDAGraph-unsafe custom ops` | Depends on the specific op |
| 8 | `_uses_cudagraph_unsafe_unbacked_symint` | `uses cudagraph-unsafe unbacked symint: {sym}` | **The second main battlefield** -- this is exactly what the bug above fixed |
| 9 | `config.triton.cudagraph_skip_dynamic_graphs` is on | `dynamic shape ops` | Off by default |

**Items 6 and 8 are the entire goal of this project.** Item 5 comes along for free.

Related config (`torch/_inductor/config.py`): `graph_partition`(623), `custom_should_partition_ops`(640),
`cudagraph_unsafe_unbacked_ops`(650), `cudagraph_skip_dynamic_graphs`(2084).

> **This also gives the P0 census a better instrument than a counter**: `should_partition` returns a **reason string**.
> Insert a hook that records the reason every time it returns, and over the 188 models we get
> the full distribution of "how many segments the graph is split into, and which rule split each segment" -- which tells us directly how much items 6/8 account for,
> i.e. the ceiling of this project. Far more informative than just counting `cudagraph_partitions`.


### NCCL measured: essentially tier 1, but it exposes a new field

`../../microbench/nccl_probe.py`, 2-GPU allreduce, fp16, sizes spanning 16384x:

| Elements | Nodes | grid x block |
|---|---|---|
| 1,024 | 3 | 1 x 128 |
| 65,536 | 3 | 16 x 512 |
| 1,048,576 | 3 | 22 x 544 |
| 16,777,216 | 3 | 24 x 544 |

**The kernel sequence is identical across the 4 sizes (3 nodes, 1 sequence).** Topology stable, kernels stable -- on this point NCCL really is "yet another kernel"; that judgment was right.

**But both the grid and `blockDim` change.** blockDim had not shown up before, and it adds one row to the "what can be changed from where" table:

| Field | Changeable from the device | Changeable from the host |
|---|---|---|
| Parameter values / gridDim / enable | yes | yes |
| **blockDim** | no, **there is no corresponding device API** | yes, `ExecKernelNodeSetParams` |
| sharedMemBytes | no | yes |
| kernel function | no | yes |
| Topology | no | no |

So NCCL falls into the "fixable from the host, not from the device" class -- or use **pre-placed variant nodes + SetEnabled** (each pre-placed node carries its own blockDim, which once again shows SetEnabled's unique value).

**And NCCL happens to have ready-made "pinning" knobs**: `NCCL_MIN_NCHANNELS` / `NCCL_MAX_NCHANNELS` (set them equal to fix the grid) and `NCCL_NTHREADS` (fixes blockDim). If grid x block stays constant across sizes after pinning, NCCL drops straight to pure tier 1, leaving only two parameters to patch: the count and the pointers.

### Problems 2 and 3 downgraded (originally overestimated)

**Problem 2 (arena overflow) -> medium-low risk.** Sizes are discovered monotonically, so **doubling** is enough: on overflow, double the arena and re-capture. Amortized, that is only O(log) re-recordings, and it converges quickly -- which is exactly an instance of the "the graph converges" claim.

There is a neat implementation that uses mechanisms we have already measured: **the planner kernel first computes the total needed for this step; if it exceeds capacity, it sets a flag and uses `cudaGraphKernelNodeSetEnabled(false)` to turn off all downstream nodes**, so the whole graph idles. The host checks the flag -> grows the arena -> re-records -> reruns. The cost is one wasted launch, but because of doubling it only happens O(log) times.
The only constraint: the input state must not already have been corrupted before the rerun, so state that is modified in place has to be rollback-able or double-buffered.

**Problem 3 (output tensor lifetime) -> medium-low risk.** I had mistaken a *design choice* of cudagraph trees for the problem itself. It deliberately **avoids** copying for performance, and that is why it needs the bug-prone liveness tracking.

We can just **copy out**: Inductor already knows which buffers are the outputs of this region, so add one copy at the end of the graph into memory from the ordinary allocator. The outputs of a training step are the loss and gradients, which are small; for inference it is a modest tensor. The cost is negligible, and correctness holds directly. Only the case of "returning a huge intermediate tensor" needs finer handling, and even then only the few tensors that actually escape get copied.

|---|---|---|---|
| 1 | **unbacked SymInt carried all the way through Inductor to the graph node** | PyTorch itself is still fixing this (those 11 places in 2026-07, bug #172728). It is upstream of us and we cannot route around it | **High** |

| 5 | RNG offset / mutation / aliasing / autograd | The mechanisms are clear, but getting them wrong gives silently garbage results | Medium |

### Is "too much engineering" a problem

No. **The PyTorch 2 paper (ASPLOS'24) is itself almost entirely engineering** -- its contribution is "works on 188 real models". The contribution of this route is the same kind, but it has to satisfy two things:

1. **The coverage number has to be presentable.** That is the only real judge
2. **At least one thing has to be more than plumbing.** Current candidates: the device planner makes data-dependent shapes graphable **for the first time** (today PyTorch just splits the graph); and the four-layer soundness framework for opaque kernels, **declare / pin / ask / break the graph** -- it replaces "unreliable observation" with "an authoritative source", which is an abstraction that can stand on its own

I ran a round of 19-agent source investigation (43 minutes, 2.5M tokens), in which one dedicated skeptic overturned several of this document's earlier conclusions.
I **went back to the source and re-verified each item below myself**; this is not hearsay.

### What was overturned, by severity

**1. ~~"One Inductor kernel covers all shapes"~~ -- I first misread this, and then measurements downgraded this FATAL again. See the quote box below.**

I measured n from 128 to 65537 producing 0 new cubins, and on that basis said the tier 1 premise holds. **The cubin count really is 1, but that cubin's block configuration is pinned to "the shape of the first trace":**

- The docstring of `sizevars.py:1149 optimization_hint()` says verbatim "Return a **concrete integer hint** for an expression"; for a backed symint that is the concrete value at trace time
- `triton.py:7735-7737`: `size_hints[prefix] = next_power_of_2(int(optimization_hint(numel)))`, written into the decorator of the generated code
- `triton_heuristics.py:3957 / 4015 / 4099`: `x = min(x, size_hints["x"])` -- XBLOCK is capped by size_hints
- XBLOCK is `tl.constexpr`, baked into the cubin; and **blockDim cannot be changed from the device side** (I measured this myself)

So: trace at 128 and run at 8192, and you get fragments with XBLOCK<=128; trace at 8192 and run at 128, and a single block does everything.
**"Runs" and "runs well" are two different things here, and this project's entire value proposition is the latter.**

> The only official way out is `mark_dynamic(..., hint_override=max)` (`var_to_hint_override` in `_size_hinting.py`) --
> which amounts to compiling the whole shape space at max. This is supported, but the cost is that every small shape runs with max's register/shared memory footprint.

> #### (Above) This FATAL has been heavily downgraded by measurement (tile configs **saturate**)
>
> The skeptic's mechanism is right, but I missed a key point: **the candidate set of tile configs is tiny, and it saturates as the shape grows.**
> Calling `triton_config` / `triton_config_reduction` directly, which is what Inductor actually uses (pure CPU, no GPU):
>
> | | How many scanned | How many configs came out | Key point |
> |---|---|---|---|
> | pointwise | 13 size_hints, spanning 5 orders of magnitude (64 -> 16.7M) | **5** | **XBLOCK=1024 alone covers 1024 -> 16.7M**; the other 4 are all below 1024 |
> | reduction | 12 (xnumel, rnumel) combinations, spanning 6 orders of magnitude | **2** | R0_BLOCK is constant at 128 throughout; XBLOCK likewise saturates at 1024 |
>
> The reason is `x = min(x, size_hints["x"])` at `triton_heuristics.py:3957` together with `TRITON_MAX_BLOCK["X"]=4096`
> and the upper bound of `_num_warps` -- once size_hint passes a threshold, the config stops changing.
>
> **So the failure mode "trace at 128, run at 8192, get fragments" is avoidable: use `hint_override` to set the compile hint to >=1024,
> and you get the optimal config for the entire range above 1024.** The only degradation is for shapes below 1024, and those kernels take only a few microseconds anyway;
> they are launch-bound rather than tile-bound -- exactly the range where graphs pay off most and tiles matter least.
>
> Caveat retained: the above is the **heuristic** path (`max_autotune` is off by default). With autotune on, it re-tunes per shape;
> matmul / conv templates go through a different autotune logic, and this conclusion does not apply to them.


**2. Tier 2's 0.73 us/node was measured on the wrong graph.**

CUDA docs (the restrictions paragraph of `CU_LAUNCH_ATTRIBUTE_DEVICE_UPDATABLE_KERNEL_NODE` in `cuda.h`, which I myself quoted earlier in this document):
for a graph that contains device-updatable nodes, **every host-side exec update requires re-running `cuGraphUpload` on the whole graph** before it can be launched again.
My 0.73/0.53 us was measured on an ordinary graph that is **not** device-updatable, and excludes the upload.
Moreover, grepping the whole PyTorch repo for `cuGraphUpload` gives **0 hits**; it never does this.
**Tier 2's budget must be recomputed; until the upload cost has been measured, it should be treated as "on the same order as re-capture".**

**3. Extern kernels cannot be eliminated, and there is no corresponding setter on the device side at all.**

- conv's ATen fallback is added back **unconditionally** (`kernel/conv.py:766-774`); it is not something a config can turn off
- conv backward returns a `FallbackKernel` directly when there is no Triton candidate
- The output buffer of `ExternKernelAlloc` is malloc'ed by ATen itself; the wrapper does not emit `empty_strided`, so **the address is not under Inductor's control**
- **Most critical: the device-side update API covers kernel nodes only. There is no device-side memset / memcpy / child-graph setter.**
  And cuBLAS split-k adds extra memset+reduce nodes -- that is a topology change, which only tier 3 can handle

-> **Conv networks, and any model that goes through the SDPA/flash fallback, are structurally out.**

**4. v0 has no deliverable intermediate form.**

The path "capture at max shape, patch only numel, keep the grid at max, extra blocks become no-ops via the mask" is wrong twice:
`_has_constant_mask` at `triton.py:8306-8320`, when `statically_known_multiple_of(numel, max_block)` holds,
**removes the mask from the kernel body entirely**; patching numel is then a complete no-op, and the extra blocks do unmasked reads and writes.
And when the mask is present, running the full max grid every step is equivalent to a static graph padded to max -- achievable with `dynamic=False` + bucketing, with no graph surgery at all.

`../../microbench/switch_hetero.cu`, GPU 5.

|---|---|---|

### FATAL 4 is downgraded too -- but the conclusion is not what the skeptic said

Original verdict: the path "v0 patches only numel, keeps the grid at max, extra blocks idle via the mask" is **neither correct nor beneficial**.

**The "not correct" half is wrong.** Measured on the generated code (`../../microbench/maskcheck2.py`, GPU 5):

| Compile mode | In the generated kernel | Is patching xnumel useful? |
|---|---|---|
| **`dynamic=True` (our scenario)** | `xnumel` is a **runtime kernel argument** (`'xnumel': 'i32'` in the signature); `xmask = xindex < xnumel`; every load/store is masked | **Useful, and safe** |
| `dynamic=False`, numel=4096 (a multiple of 1024) | `xnumel = 4096` is hardcoded in the body; `xmask = tl.full([XBLOCK], True)` -- the mask is effectively removed | Useless |
| `dynamic=False`, numel=4097 | `xnumel = 4097` is hardcoded; the mask is real | Useless (hardcoded in the body) |

`_has_constant_mask` does exist, but it only triggers when numel is **statically known**, i.e. under `dynamic=False`.
We use `dynamic=True` throughout, and a symbolic numel can never be judged true by `statically_known_multiple_of`.
Correctness was measured as well: running n=777 on the max grid, the first 777 elements are correct, and past element 777 **not a single byte was written**.

**The "not beneficial" half has the right conclusion but the wrong reason.** The skeptic said "every step does the work of the full max" -- not so: a masked-out block
exits as soon as it tests the mask and does almost no memory access. The real cost is **scheduling overhead**:

| Actual n | Exact grid time | Max grid (4096) time | Extra blocks | Extra overhead |
|---|---|---|---|---|
| 1,024 | 2.05 us | 8.52 us | 4095 | **+6.47 us** |
| 8,192 | 2.85 us | 8.41 us | 4088 | +5.56 us |
| 65,536 | 3.06 us | 8.30 us | 4032 | +5.24 us |
| 1,048,576 | 6.09 us | 9.28 us | 3072 | +3.19 us |
| 4,194,304 | 20.43 us | 20.34 us | 0 | -0.09 us |

**About 1.5 ns per idle block.** Cheap on its own, but 4000 idle blocks ~= +5 us/kernel,
and multiplied by 3000 kernels in one graph that is **+15 ms/step** -- that really would eat all of the gain.

**So the real conclusion is: v0 must include grid patching; patching scalars alone is not enough.**
And grid patching is exactly the easiest piece -- the planner calling `SetGridDim` measured 0.05 us/node,
and once the grid is exact, all of the extra overhead in the table above goes to zero.

This is not a structural obstacle, just "this item has to be in the minimal set of the first version".

This table is now just a price list of "how much you pay if you do not patch the grid".






## The fake tensor survey path: main has already fixed it

**Bottom line first: once our self-built main is installed, the most naive approach just works.** It does not work on the 2.11 that ships with the container,
but that is a version problem already fixed upstream, not a missing API.

The failure looks like this:

```
AssertionError: fake mode (...) from tracing context 0
               doesn't match mode (...) from fake tensor input 0
```

Cause: Dynamo itself creates two `FakeTensorMode`s (one for tracing, and one handed to the backend,
`backend_fake_mode`), but `OutputGraph.example_inputs()` returns the **caller's original** tensors,
so `detect_fake_mode()` sees the two sides disagree.
**Wrapping it in `torch._guards.tracing(TracingContext(my_mode))` does not help**: measured, Dynamo still installs its own
TracingContext, the two ids differ every time, and neither is the one I passed in.

main HEAD fixes this in two places:

| Location | Change |
|---|---|
| `torch/_guards.py:1531-1552` | `detect_fake_mode` now authoritatively returns the TracingContext's mode; the comment states "any fake tensor from another mode will be re-fakified by the caller" |
| `torch/_functorch/_aot_autograd/frontend_utils.py:111-117` | When `process_inputs` meets an input from a foreign mode it clones it in with `fake_mode.from_tensor(x)`; the comment states this is for cross compilation |

So the right way to take this path is **to install the self-built torch first**, not to wrestle with 2.11.


### Measured (after installing the self-built main): the fake path works, but the definition of "success" has to change

Running the naive approach on torch 2.15.0a0+git71b3251, the result is that **compilation runs to completion, then the run phase errors out**:

```
torch._subclasses.fake_tensor.FakeTensorDeviceMismatchError:
    Expected all tensors to be on the same device, but found at least two devices, cuda:0 and meta!
```

The stack lands in `torch/_inductor/cudagraph_trees.py:824 run`, i.e. at the moment cudagraph actually tries to record.
**That is exactly the part we do not need.** Dynamo, AOTAutograd, GraphLowering and Scheduler
all ran to completion, `graph_partition` ran too, and the data is all there:

| Model | Nodes that cannot enter the graph | Partitions (fwd, bwd) | Reason |
|---|---|---|---|
| Two Linear layers | 0 | 1, 1 | none |
| One with `nonzero` | 3 | 4, 1 | `unbacked binding ops` x1, `cpu ops` x2 |

`torch.cuda.memory_allocated()` stays at **0** throughout.

So the harness criterion becomes: **as soon as `graph_partition` has run, it counts as success**,
and a `compiled_but_not_run` flag is recorded. This also fits the semantics of the survey better: what we tally is compile-time decisions in the first place.

An observation on the side: besides the unbacked node, that `nonzero` model also brings in **2 `cpu ops` nodes** --
data dependence drags part of the computation onto the CPU along with it, which is a second, independent reason for splitting the graph.

### Three alternative paths (measured on 2.11)

| Path | Result |
|---|---|
| A 6-line custom Dynamo backend that clones example_inputs into the TracingContext's fake mode and then calls `compile_fx` | **Works**; Dynamo -> AOTAutograd -> GraphLowering -> Scheduler all run through |
| No Dynamo: `make_fx(...)` or `torch.export.export(...)` under your own fake mode, then `compile_fx(gm, [your own fake inputs])` | **Simplest**; needs no TracingContext manipulation at all |
| `torch._inductor.standalone_compile` | **Does not work**: internally its `copy.deepcopy(gm)` re-fakifies the lifted parameters into a brand-new mode (the id change was verified directly) |

The `torch.export` path has a pitfall: export creates **its own** fake mode for the placeholders' `meta['val']`
(`torch/_export/non_strict_utils.py:447`), while the parameters of `ep.module()` stay in your mode.
So you must feed **your own** fake inputs; feed it the placeholders' own values and they mismatch again.

### Memory cost: one CUDA context, zero tensors

| Item | Measured |
|---|---|
| GPU memory for the whole fake compilation | **520 MiB**, all of it the CUDA primary context |
| `torch.cuda.memory_allocated()` | **0** |
| `torch.cuda.memory_reserved()` | 2 MiB |
| Stopping after `codegen()` (no cubin compilation) | still 520 MiB, showing that the context is the entire cost |
| Calling `torch.cuda.get_device_properties(0)` alone | **does not create a context**; the process does not show up in `nvidia-smi` at all |

**A real, visible GPU is required**: `CUDA_VISIBLE_DEVICES=""` crashes in AOTAutograd's joint trace
with `hasPrimaryContext expects a valid device index`. So "never touching the GPU at all" is not possible,
but a constant 520 MiB overhead + zero tensors + zero kernels has a negligible effect on other people's jobs.

### Another 40% of compile time can be saved

The survey only needs to run up to scheduling; whether cubins get compiled does not matter.
Patch `torch._inductor.graph.GraphLowering.compile_to_module` so that it raises right after calling `self.codegen()`:
Scheduler and codegen still run, cubin compilation is skipped, and a single model drops from about 4.1 s to about 2.4 s.
Over 188 models that is a real difference.




### Unexpected finding: shape computation on the CPU may be a more pervasive blocker than data dependence

A one-off case I checked in passing during the survey turned out to matter more than expected.

**MobileNet-V2**, as standard a conv net as there is, with no data-dependent ops at all and zero Dynamo graph breaks:

| Metric | Value |
|---|---|
| Nodes that cannot enter cudagraph | 72 |
| of which `cpu ops` | **71** |
| of which `DeviceCopy ops` | 1 |
| Partitions | 2 segments forward, 2 segments backward |
| Segments where cudagraph is ultimately given up | **all 2** |

Where those 71 nodes come from (found with `../../survey/_cpuops_probe.py`):

```
by origin:   71  aten.cat.default, aten.unsqueeze.default
              1  prims.device_put.default
by ir_type:  70  ComputedBuffer   1  ConcatKernel   1  DeviceCopy
by device:   71  cpu              1  cuda:0
```

**They are `cat` / `unsqueeze` on the CPU, i.e. scalar computation under dynamic shapes that has been materialized into CPU tensors.**

Control: **ResNet-18 has 0**, with the same BatchNorm and the same `dynamic=True`.

#### Tracked all the way down to a three-line minimal repro: `nn.ReLU6`

Trying one feature at a time (`../../survey/_minrepro.py`, `_relu6.py`, `_relu6_dyn.py`):

| Form | `dynamic=True` | `dynamic=False` |
|---|---|---|
| `nn.ReLU6()` | **4 CPU nodes** | 0 |
| `nn.Hardtanh(0.0, 6.0)` float bounds | **4** | 0 |
| `nn.Hardtanh(0, 6)` **integer** bounds | 0 | 0 |
| `F.hardtanh(x, 0.0, 6.0)` called directly | 0 | - |
| `x.clamp(0.0, 6.0)` | 0 | - |
| `F.relu6(x)` | 0 | - |
| `nn.ReLU()` / depthwise conv / `adaptive_avg_pool2d` / `Dropout` | 0 | - |

All three conditions are required: **`dynamic=True`** + **the bounds are passed through `nn.Module` attributes** + **those attributes are floats**.

`nn.ReLU6` hits all three; its definition is

```python
class ReLU6(Hardtanh):
    def __init__(self, inplace=False):
        super().__init__(0.0, 6.0, inplace)   # float

def forward(self, input):
    return F.hardtanh(input, self.min_val, self.max_val, self.inplace)  # reads module attributes
```

In other words: **under `dynamic=True`, float attributes on an `nn.Module` are symbolized as dynamic scalars
and then materialized into CPU tensors** (`unsqueeze` + `cat`), which `device_put` then copies back to the GPU.
Integer attributes take a different path and are not affected. Neither are literals or the functional call form.

This explains MobileNet-V2's 71: it has dozens of `ReLU6`s.

**This is a clean bug that can be reported upstream.** A three-line repro, affecting every model that uses `nn.ReLU6`
(the whole MobileNet family, some EfficientNets). The self-contained repro script is `../../survey/repro_relu6.py`.
Per the repo's AI policy, reporting it requires confirmation from Xinwei first.

#### But it is also an interpretation trap, and we have to spell that out ourselves first

These partitions **really happen**; PyTorch really does split the graph this way today, so the data is not wrong.
The issue is **attribution**:

> If `non_gpu_ops` dominates Figure 2, and a large part of it comes from an upstream bug that three lines of code can fix,
> then the argument "a DynaGraph is needed to solve this" would not hold up -- a reviewer would ask straight away,
> "why didn't you just fix that bug?"

So once the data is in, **`non_gpu_ops` has to be broken down**, into at least two categories:

| Category | Example | What it means for the project |
|---|---|---|
| Upstream-fixable one-off cases | Float attribute symbolization in `nn.ReLU6` | **Cannot count as a reason for the project**; should simply be reported upstream |
| Structural CPU computation | Size/offset/scheduling computation that genuinely needs the host | This is DynaGraph's target |

To do this, `instrument.py` has to record the `origins` of every `cpu ops` node
(`_cpuops_probe.py` already has the code for it). It must not be changed until this round has finished running.

#### Broken down, and it is bad news for the argument: MobileNet's 71 **come 100% from this bug**

What `../../survey/_attribution.py` does is simple: replace every `nn.ReLU6` in the model with an equivalent module whose bounds are written as
literals (`F.hardtanh(x, 0.0, 6.0)`), leave everything else untouched, and measure again.

| Model | As is | After replacing ReLU6 | How many replaced |
|---|---|---|---|
| `mobilenet_v2` | 72 non-GPU nodes (71 `cpu ops` + 1 `DeviceCopy`) | **0** | 35 |
| `mobilenet_v3_large` | 0 | 0 | 0 (it uses Hardswish, not ReLU6) |
| `efficientnet_b0` | 0 | 0 | 0 (uses SiLU) |

**Down to zero.** That is, all 71 CPU nodes in MobileNet-V2 come from that upstream bug that three lines of code can fix;
not one of them is structural.

**The argument has to be adjusted accordingly**:

> **The `cpu_ops` in CV classification models cannot be used as a reason for the project.** They are a symptom of an upstream bug;
> the right move is to report the bug, not to use it to argue that a new system is needed.

This in turn makes the argument cleaner: CV classification models (ResNet / ViT / ConvNeXt / EfficientNet / the big TIMM batch)
**really can already go into cudagraph as a full graph**, all the more so once the ReLU6 case is subtracted.
The project's target is not there; it is in **scenarios with data dependence**:
7 of the eight probes above have problems, and in those 7 the cause is `unbacked_binding` and the CPU computation that comes with it,
not some lowering bug that could be fixed on its own.

#### But the detection models' CPU nodes **cannot be subtracted** -- this is the real target

Applying the same breakdown to detection models gives the exact opposite of MobileNet:

| Model | As is | Replaceable ReLU6 | After replacing | Cannot be subtracted |
|---|---|---|---|---|
| `ssd300_vgg16` | 99 (97 `cpu ops` + 2 copies) | **0** | **99, not one fewer** | **97** |
| `ssdlite320_mobilenet_v3_large` | 155 (152 + 2 + 1 `unbacked`) | 24 | 106 (104 + 1 + 1) | **104** |

The backbone of `ssd300_vgg16` is VGG, which has no ReLU6 at all, so none of its 97 CPU nodes can be subtracted.
`ssdlite320` still has 104 left after subtracting ReLU6's contribution.

**This is the structural category.** Breaking down those 97 nodes of `ssd300_vgg16` by source
(`../../survey/_cpuops_probe.py`):

| Source ops | Nodes |
|---|---|
| `aten.add` + `aten.cat` + `aten.clone` | 57 |
| `aten.cat` + `aten.clamp_max` + `aten.clamp_min` | 12 |
| `aten.add` + `aten.cat` + `aten.reshape` | 9 |
| `aten.cat` | 7 |
| `aten.cat` + `aten.unsqueeze` | 6 |
| `aten.clamp_max` + `aten.clamp_min` + `aten.repeat` | 5 |
| `aten.clamp_max` + `aten.clamp_min` | 1 |

The node types are 83 `ComputedBuffer` + 14 `ConcatKernel`, all on `cpu`.

**This is SSD's anchor generation**: `repeat` tiles the anchors over every position, `add` adds the center offsets,
`clamp_min/clamp_max` clip them to within the image bounds, and `cat` concatenates the anchors from each feature-map level.
It lands on the CPU because it depends on the spatial sizes of the feature maps, which are symbolic under dynamic shapes.

**For the design this is good news, and it has been verified, not guessed.**
`../../survey/_purity2.py` looks up in Inductor's buffer table what each CPU node reads, and on which device:

| Metric | Value |
|---|---|
| Scheduled nodes on the CPU | 91 (255 buffers in the graph in total) |
| Reads from **CPU** buffers | 96 |
| Reads from **GPU** buffers | **0** |

**Not a single one reads the GPU.** These hundred-odd nodes form a **fully independent computation chain that depends only on shapes**;
the planner kernel can move the whole chain onto the device without waiting for any GPU result.
This is the most direct and least controversial application of the DynaGraph mechanism.

By contrast, the same model has only 1 `unbacked_binding`, coming from NMS
(`torchvision/_meta_registrations.py:173` explicitly calls `ctx.create_unbacked_symint()`;
"how many boxes to keep" is a true data dependence). **A hundred to one in count, and exactly the reverse in difficulty**:
the pure-function category covers the vast majority of nodes and has no theoretical obstacle; the data-dependent category is small in number but the hard nut to crack.
The roadmap should tackle the former first.

So once the attribution is broken down, the conclusion is clear:

| Category | Scale | What to do |
|---|---|---|
| `cpu_ops` in CV classification models | MobileNet-V2's 71, **zero after subtraction** | Report the upstream bug; **cannot be used as a reason for the project** |
| `cpu_ops` in detection models | About 100 per model, **cannot be subtracted** | **DynaGraph's target** |
| `unbacked_binding` + the CPU computation that comes with it in data-dependent scenarios | 7 of the eight probes | **DynaGraph's target** |

The same scrutiny also has to be applied to `unbacked_binding`: how much of it is true data dependence,
and how much is merely a specialization that PyTorch has not implemented yet.

**Why this line matters:**

1. It shatters the graph **without needing any data dependence**. A pure conv net with zero graph breaks still gets both segments shut out of cudagraph.
   If this holds on more models, "data dependence" is not the only target, and perhaps not even the main one.
2. It is **exactly what DynaGraph's core mechanism is meant to solve**. The sizes computed on the CPU
   are exactly the quantities this project wants to move into the device planner kernel. The earlier design put its weight on
   unbacked SymInt; this finding suggests the `non_gpu_ops` line may have broader coverage and also be easier to do
   (size computation is a pure function, without the fundamental difficulty of data dependence, where you "must wait for the device to finish").
3. It explains something that had long been unclear: why many models that look perfectly fine get no benefit from
   `mode="reduce-overhead"`.

Once the full data is in, the share of `non_gpu_ops` in Figure 2 is the single number most worth looking at in this round of the survey.

### Methodology alert: the fake-mode crashes are not random, they single out the most interesting models

Earlier I verified that "fake mode and real tensors give the same compile-time conclusions". That conclusion was correct, but **incomplete**.
It only covered models that "ran through on both sides". The real question is: **are the ones that crash random?**

No. In the interim data (72 models), 12 are `NoResult` (subprocess segfault):

```
tv:mobilenet_v2            timm:mobilenetv2_100      timm:rexnet_100
tvdet:ssdlite320_mobilenet_v3_large                  timm:cspdarknet53
timm:cait_m36_384          timm:convit_base          timm:botnet26t_256
timm:crossvit_9_240        timm:eca_botnext26ts_256  timm:levit_128
timm:nfnet_l0
```

**The entire MobileNet family is on the list.** And MobileNet is exactly the class identified above that produces a large number of CPU nodes because of `nn.ReLU6`.
The causal chain is clear: CPU nodes introduce `DeviceCopy`,
and fake mode segfaults precisely on `DeviceCopy`.

The result is textbook **selection bias**:

| | Interim stats (72 models) |
|---|---|
| torchvision classification compiled successfully | 16/20, of which **full-graph cudagraphable 16/16 (100%)** |
| TIMM compiled successfully | 31/45, of which **full-graph cudagraphable 31/31 (100%)** |
| Models with `cpu_ops` | **only 1 left** (`ssd300_vgg16`, 91 nodes) |

It looks as if "the vast majority of models already go into a cudagraph as a full graph, so the project is unnecessary".
**In reality, the problematic models all crashed and disappeared from the denominator.**
If Figure 1 were drawn from this, its conclusion would be inverted.

#### One layer deeper, the problem is worse than "the crashes are biased": fake mode **silently truncates**

To close the validation gap I picked `tvdet:ssd300_vgg16` -- it has 91 `cpu_ops` but **did not crash** under fake,
which makes it the right case for answering "are the numbers accurate when it does not crash". They are not:

| Field | fake | real tensors |
|---|---|---|
| Nodes that cannot go into the graph | 92 | **101** |
| `cpu_ops` | 91 | **98** |
| `device_copy` | 1 | **2** |
| `unbacked_binding` | **0 (not seen at all)** | 1 |
| Partitions per `graph_partition` call | `[2]` | `[2, 2, 2, 1, 1, 0, 1, 1, 1]` |
| Partitions that ultimately gave up on cudagraph | 1 | **4** |
| Full-graph skip | none | **1** |

**The key is those last two rows: under fake only 1 subgraph was compiled; under real tensors there are 9.**
Dynamo graph breaks produce multiple subgraphs; fake mode crashes after the first subgraph (`AcceleratorError`),
and the remaining 8 were never compiled. My success criterion was "it counts as success once `graph_partition` has run",
so this truncated record went into the statistics as if it were complete data.

So fake mode has two problems:

1. **The crashes are selection-biased**: it crashes specifically on models with CPU nodes (`DeviceCopy` triggers the segfault).
2. **Even when it does not crash, it silently truncates**: for multi-subgraph models only the first subgraph is counted, so the numbers are a lower bound.

**Conclusion: fake mode can only be used for scouting, not for final data. The whole survey switches to real tensors.**

Feasibility has already been measured: SSD300 single-process peak memory is **5252 MiB**, with complete data (all 9 subgraphs counted).
Of the 131 models only about 5 exceed 1 billion (10^9) parameters (GPT-J 6 B, Blenderbot 2.7 B, etc.) and need separate handling;
the rest at `--jobs 3` take about 18 GB, which fits on GPU 5.

The fake data is kept in `../../survey/results_FAKE_incomplete.jsonl`, as evidence for "why fake cannot be used".

**The more general lesson**: to check whether a measurement method is good enough, ask three questions; missing any one of them can invert the conclusion:

1. Do the numbers agree when both sides succeed? (asked in the first round of validation)
2. **Is failure correlated with the phenomenon being measured?** (only thought of in the second round; the answer is yes)
3. **Can the "success" criterion mistake truncated data for complete data?** (only thought of in the third round; the answer is yes)

For the problem that the list is not representative enough, the most direct approach is to write the **core pattern** of those categories in plain PyTorch and measure it,
without installing PyG / DGL / TorchSparse just for one probe. The six probes are in `../../survey/models_extra.py`;
each keeps only the small piece that produces the data dependence. Real tensors, `dynamic=True`, `mode="reduce-overhead"`.

### Three conclusions

**1. The exact opposite of the CV classification models.** For torchvision classification and TIMM, 100% of the successfully compiled models go into
a cudagraph as a full graph, while among these eight categories **7/8 have problems**; the only clean one is the pure-aggregation `gnn`. So the early signal "the vast majority of models are fine already"
came from a badly chosen list, not from the truth.

**2. Both configurations are bad, they are just ugly in different places.** Under the default configuration Dynamo breaks the graph into 2-5 pieces,
one cudagraph per piece, with a return to the host in between; with capture turned on there are no graph breaks, but Inductor cuts the graph into 4-5 partitions,
and MoE does not compile at all. **No configuration lets these models go into a cudagraph as a full graph**, and that is exactly what the project sets out to solve.

**3. `unbacked_binding` and `cpu_ops` are coupled, not two independent lines.**
Every problematic probe shows both reasons at the same time. Data dependence drags part of the computation onto the CPU along with it
(computing masks, offsets, lengths), and those quantities are precisely what a planner kernel should compute on the device.
This is more unified than the earlier plan of "handling the unbacked line and the non-GPU line separately", which is good news for the design.

**The clean `gnn` case is informative too**: the number of output rows of `index_add_` is determined by the number of input nodes,
which is not a data dependence, so it fits as a full graph. In other words, the real trouble in GNNs is in the **sampling stage**, not the aggregation stage.
Adding the `gnn_sample` probe confirmed this directly: the same GNN, but as soon as the "filter edges by seed" step is added,
it immediately becomes 4 partitions + `unbacked_binding`.

**4. The two categories Xinwei cares about most happen to be the two hardest.** `moe` (top-k routing) and `decode` (variable-length KV)
are **the only two probes that fail to compile outright once capture is turned on**, one with `GuardOnDataDependentSymNode`,
the other with `BackendCompilerFailed`. They are exactly the core patterns of LLM serving,
and exactly the reason vLLM / SGLang had to resort to piecewise cudagraphs.
On these two categories today's PyTorch is not "cut into fragments"; it **does not compile at all**.


### An early signal to keep an eye on: CV classification models may be fine already

Among the 65 records of the first round (discarded, because old and new code were run mixed together), **every successfully compiled torchvision classification and TIMM model
was full-graph cudagraphable; not a single one was partitioned**. All 7 detection/segmentation models failed to compile.

This is not a conclusion, but it points to a risk that has to be faced squarely:

> **If most of the 131 models already go into a cudagraph as a full graph, Figure 1 would not stand, and the project's motivation would have to be rewritten.**

Moreover, our list is quite likely **not representative enough**. torchvision classification + TIMM total 81 models,
62% of the list, and this category is precisely the most regularly written models with the least data dependence.
The paper's 80 TorchBench models include a lot of "messy" real-world code; we did not install torchbench, so that is exactly the part we missed.
What Xinwei asked for, "arbitrary messy open-source training code", is barely represented in the current list.

The categories that really should have data dependence are the following, and in the current list they are **either absent or all fail to compile**:

| Category | Status in the list |
|---|---|
| Detection / segmentation (NMS, topk, boolean indexing) | 7 present, **all failed to compile** in the first round |
| GNN (neighbor sampling, variable-length edge lists) | **none**; needs PyG/DGL |

| Point cloud / sparse convolution (the number of active voxels varies with the input) | **none** |
| Recommendation (jagged tensors, variable-length user history) | **none** |
| The decode loop of LLM serving | **none**, and this is one of the targets Xinwei cares about most |

So two things have to be done at the same time: first finish running the current 131 to get a baseline, then extend the list according to the table above.
If after extending it the "fits as a full graph" ratio is still high, then that is the real conclusion, and the topic has to be adjusted accordingly, rather than cherry-picking data.


## Reference point: what the eval of PyTorch 2 (ASPLOS'24) looks like

The route Xinwei set is to copy this paper's methodology: not competing over a few percent of speed, but **reporting coverage over a large number of messy real-world models**.
Numbers checked against the paper text (Table 1 / Table 3 / Sec 6 extracted with `pdftotext`):

**Scale**: TorchBench 80 + HuggingFace 46 + TIMM 62 = **188 models** (the abstract says "180+").

**The coverage rows of Table 1**, which is the table we need to mirror:

| | TorchBench | HuggingFace | TIMM |
|---|---|---|---|
| Runs under TorchDynamo | 74 (93%) | 46 (100%) | 62 (100%) |
| Runs under TorchScript | 36 (45%) | 0 (0%) | 61 (98%) |
| 0 graph breaks | 52 (70%) | 41 (89%) | 62 (100%) |
| 1-9 breaks | 6 (8%) | 1 (2%) | 0 |
| >=10 breaks | 16 (22%) | 4 (9%) | 0 |
| Operator capture rate | 91.8% | 99.8% | 100% |

**Metric definitions**: coverage is simply the plain fraction "number of models that run / number of models attempted".
Speedup is the geometric mean relative to eager, **computed only over the models that run** (the Table 3 caption states it explicitly:
"Only working models are included in speedup calculation").
Experiments are repeated 100 times, with 3 warmup runs and a 30-minute timeout per model; **a timeout counts as a failure**.
The headline is a 2.27x inference / 1.41x training geometric mean over 180+ models on A100.

|---|---|---|---|---|
| One row for each of the three suites | ? | ? | ? | ? |

Pair it with a breakdown chart **grouped by reason** (`unbacked_binding` / `non_gpu_ops` / `device_copy` /
`cudagraph_unsafe_custom_op` / ...), showing "which one is the blocker".
These two charts are also the basis for choosing the topic: if the vast majority of models already have 0 partitions, the project would not be needed.

## First hard data from the P0 survey: data dependence is blocked at two layers, and the magnitude is larger than expected (2026-09-17)

While building the harness I first calibrated it with three toy models, and the result directly produced the quantitative evidence needed to justify the project.
Each model is just two `Linear` layers: `plain` has no data dependence, `datadep` is `y[y.sum(-1) > 0]`,
`nonzero` is `y[torch.nonzero(y[:,0] > 0).squeeze(-1)]`.

| `capture_dynamic_output_shape_ops` | Model | Dynamo graph breaks | Times Inductor ruled "cannot go into the graph" | Final partitions |
|---|---|---|---|---|
| False (**default**) | plain | 0 | 0 | - |
| False (**default**) | datadep | 0 | 0 | - |
| False (**default**) | nonzero | **1** | 0 | - |
| True | plain | 0 | 0 | - |
| True | datadep | 0 | 12 | **7** |
| True | nonzero | 0 | 9 | **4** |

Two conclusions:

**1. Data dependence faces two checkpoints, and under the default configuration the first one already blocks it.**
By default Dynamo breaks the graph as soon as it meets `aten.nonzero.default`, reporting
"Operator's output shape depends on input Tensor data".
Once the graph is broken Inductor never sees it, so `should_partition` never returns True even once --
**not because there is no problem, but because the problem has been moved one layer up**. If the survey does not turn this switch on, all Inductor-layer data is 0,
and it would reach the wrong conclusion that "there is no partitioning problem".

**2. With the switch on, data dependence lands in Inductor, and a single operator cuts two Linear layers into 4-7 partitions.**
That is the magnitude of what the project sets out to solve: not "occasionally losing one cudagraph",
but a single `nonzero` being enough to smash a small graph into seven pieces.

Inductor prints the reason itself in the log, so it can be scraped directly:

```
cudagraph partition due to unbacked binding ops. Found from :
   File ".../models.py", line 27, in forward
    return y[torch.nonzero(y[:, 0] > 0).squeeze(-1)]
cudagraph partition due to non gpu ops
cudagraph partition into 4 partitions
```

Note the second kind of reason, **non gpu ops** -- operators on the CPU also cut the graph; this is a separate line, independent of unbacked.

### Four must-haves for the harness (each one learned the hard way)

| Config | What happens if it is not set |
|---|---|
| `force_disable_caches = True` | The second compile of the same model hits the cache directly and **does not go through the scheduler**, so the stats silently become 0 |
| `mode="reduce-overhead"` | Without cudagraphs enabled, the semantics of `should_partition` flip (every node "does not go into the graph"), so the counts are meaningless |
| `capture_dynamic_output_shape_ops = True` | The data dependence is broken off at the Dynamo layer and Inductor never sees it |
| `capture_scalar_outputs = True` | Same as above, for `.item()` and the like |

Each model runs in an **isolated subprocess**: Dynamo/Inductor crashing on messy models is the norm,
one crash must not take the whole batch down with it, and the global config and compile caches do not pollute each other.
The harness is in `../../survey/`: `runner.py` handles process isolation, `instrument.py` the hooks, `report.py` the aggregation.

### The pitfalls of each of the three hooks (all measured)

**`should_partition` is called about 3 times per node** (once each in `reorder_for_minimizing_partition` and other places);
without deduplicating by `(graph_id, node_name)` you overcount threefold. Measured on the same model: 12 before dedup, 4 after.

**`counters["inductor"]["cudagraph_partitions"]` cannot be used as the partition count**, for two reasons:
it is only incremented when `len(partitions) > 1` (`scheduler.py:11979`), so **an empty counter does not mean no partitioning happened**,
it may also be exactly 1 partition; and it accumulates across forward/backward.
The reliable approach is to hook `Scheduler.graph_partition`, which returns `(partitions, signatures)`;
the partition count is `len(partitions)`, and `signature.skip_cudagraph` also tells you which partitions ultimately still gave up on cudagraph.
Measured on the same model: forward 4 partitions, backward 3, while the counter shows 7.

**`log_cudagraph_skip_and_bump_counter` must be rebound separately in four modules**:
`cudagraph_utils` / `output_code` / `compile_fx` / `cudagraph_trees` each did their own `from ... import` of this name,
so changing only the place where it is defined has no effect at all. In addition, upstream double-prefixes the message as
"skipping cudagraphs due to skipping cudagraphs due to ...", which normalization has to strip.

**Partition reasons are not available before main.** In the 2.11 that ships with the container, `should_partition` only returns `bool`;
the reason string exists only on main (`-> str | None`). This is also one concrete reason a self-built branch is required:
with 2.11 you can only count "how many nodes cannot go into the graph", not "why".

## The three remaining SERIOUS items, measured and closed (2026-09-17, GPU 5, correctness checks only, no timing numbers taken)

### S1 - grid bounds: 0 is not allowed, but the grid **can go far beyond the capture-time value**

`../../microbench/grid_zero.cu`:

| Scenario | Result |
|---|---|
| `mark<<<0,32>>>` ordinary launch | `cudaErrorInvalidArgument` -- **grid 0 is not a legal launch in CUDA at all** |
| numel==0 at capture time | PyTorch skips the launch outright => **the node is not in the graph and cannot be added back later** |
| Device-side `SetGridDim(node, 0)` | **Silently ignored**; the node keeps its previous grid (4->0 still runs 4 blocks) |
| Device-side `SetEnabled(node, 0/1)` | Clean; 4 -> 0 -> 0 -> 4 all correct |
| Device-side change of the grid from the capture-time **4 to 4096** | **Correctly executes 4096 blocks (1024x)** |

Two conclusions:

1. **The planner must clamp to `max(1, g)`; "nothing to do this step" must be expressed with `SetEnabled(0)`, not with grid=0.**
   Otherwise it is a silent error: the node reruns with the previous step's grid and writes garbage.
2. **The grid can grow, so "capture-at-max" is not a grid-level requirement.**
   This directly overturns the premise of the FATAL 4 table above -- there is no need to build the graph at the max shape and rely on masks to idle;
   build the graph at any typical shape and set the grid to the exact value at run time, and the +3~6.5 us/kernel of waste **goes to zero**.

### S2 - RNG: the philox increment is indeed frozen at capture, but the constraint is narrower than expected

`../../microbench/rng_increment.py`, reading the offset field of `get_rng_state()` after each replay:

| n at capture | Offset increment per replay |
|---|---|
| 1,024 | 4 |
| 4,096 | 4 |
| 65,536 | 4 |
| 1,048,576 | 4 |
| 4,194,304 | **16** |

Graph-safe RNG itself works: the dropout masks of two consecutive replays differ, with 50.0% overlap (= chance level).

The key point is that the unit of the increment is **offsets consumed per thread**, not per element.
From n = 1K to 1M the increment stays 4, because the grid grows with n and the work per thread stays the same;
at 4M the grid gets clamped, each thread has to loop 4 times, and only then does the increment become 16.

So there is only one danger: **at run time each thread does more work than at capture time** (increment too small => adjacent steps reuse the same
segment of the philox stream => dropout masks are correlated across steps). As long as the planner makes the grid grow linearly with n and does not hit
Inductor's grid limit, the frozen increment is correct.

> Rule: **for graphs that contain RNG, the capture point must be the shape with "the most work per thread"** (usually the max shape),
> or the shape range must be restricted to below the grid saturation point. This is a narrow, checkable precondition, not a global requirement.

### S3 - Triton global scratch: it is indeed allocated per grid, but it does not overlap with the kernels that "need a larger grid"

`torch/_inductor/runtime/static_triton_launcher.py:484` allocates
`grid_x * grid_y * grid_z * global_scratch_size` on every launch, and cpp-wrapper uses the same formula
(the comment at `codegen/cpp_wrapper_gpu.py:717` says it plainly: "the kernel writes its slot at offset
(pid * scratch_size)"). **Indexed by pid => growing the grid past the capture-time value is an out-of-bounds write.**

But measured (`../../microbench/scratch_probe.py` / `scratch_tma.py`):

| kernel | Uses of `make_tensor_descriptor` | `global_scratch_size` |
|---|---|---|
| pointwise / reduction / layernorm / matmul (default path) | 0 | All 5 metadata entries in the cache are 0 |
| `max_autotune` + persistent TMA matmul | 10 | 9 of 29 entries > 0, 256 B/CTA |

And the meta of those TMA kernels is `'grid_type': 'FixedGrid'`, `NUM_SMS: tl.constexpr = 132`;
**the grid does not depend on the shape**, and a tile loop consumes all the work. In other words:
**the kernels that need grid-proportional scratch are exactly the kernels whose grid does not vary with shape.**
In today's Inductor the two conditions never occur together.

The only remaining risk is "a user hand-writes a TMA kernel whose grid varies with shape", and the fix is straightforward:
the template pre-allocates scratch for the max grid. Recording this under known limitations is enough; it is not a blocker.


### Final status of the four FATAL items

| # | Original verdict | Current status |
|---|---|---|
| 1 | Triton tile config is pinned to the trace shape | **Downgraded** -- configs saturate; XBLOCK=1024 covers 1024->16.7M; reductions spanning 6 orders of magnitude have only 2 configs. Compiling with `hint_override` to >=1024 is enough |
| 2 | extern kernels cannot be removed + no device-side memset setter | **Downgraded** -- SWITCH bodies can be heterogeneous (measured), cuBLAS can go inside a body (measured), an explicit workspace eliminates alloc nodes (measured) |
| 3 | tier 2 needs a re-upload | **Downgraded** -- only triggered when host-side exec update is mixed in. Pre-placed nodes + `SetEnabled` and SWITCH are both device-side; **no host-side function swap is needed at all** |
| 4 | v0 has no deliverable intermediate form | **Downgraded** -- the "incorrect" half of the claim is falsified (under dynamic=True the mask is present and xnumel is a runtime parameter); the "no benefit" half holds, but it only means **v0 must include grid patching**, which is the easiest piece (0.05 us/node) |

**Revised tiering (all device-side, no host involvement, no re-upload):**

| Tier | What it handles | Mechanism | Cost |
|---|---|---|---|
| 1 | Parameters, grid | planner `SetParam` / `SetGridDim` | 0.05 us/node |
| 2a | Different kernel function / blockDim / smem | Pre-placed variant nodes + `SetEnabled` (each node carries these three itself) | 0.85 us/empty slot/point |
| 2b | Different **node count** (topology) | Heterogeneous SWITCH bodies | 11 us/point, independent of the number of variants |
| 3 | Genuinely new, never-seen code | Re-capture | 20 ms for 3000 nodes, bounded number of times |

2a and 2b cross over at V~13. Empty SWITCH slots are free, but they cannot be filled in afterwards; adding a variant requires re-recording.


### The skeptic's assessment

> The mechanism itself works. Whether the goal "any dynamic-shape model -> one graph covering the entire shape space" can be reached is an open question.
> What the skeptic considered realistically deliverable at the time: **inference subgraphs that are pure Triton, have no control flow, have no data-dependent shapes, and for which the user explicitly declares a narrow [min,max] range**,
> capturing one template at the max shape to cover a **narrow** range -- i.e. "reduce N graphs to a few", not "reduce them to one" --
> with the estimate that each such graph would perform **worse** on the small shapes in its range than today's per-shape graphs.

### What this means for the project

Both legs established earlier need to be re-evaluated:

- **The "non-LLM dynamic models" leg is the most affected** -- GNN / point cloud / recommendation happen to depend heavily on data-dependent shapes and extern kernels (scatter/sort/sparse conv), and both of these fall outside the scope the skeptic above considered deliverable
- **The "LLM serving eliminates piecewise" leg still stands**, but the framing must change: not "one graph replacing 67", but "reducing 67 graphs to a few",
  and the benefit comes mainly from **capture memory and cold start** (the 20 GB / 36-65 s numbers), not steady-state latency

**The next step is not writing code but first measuring three numbers** (see the next section, "Revised P0").

## 10. Roadmap

**P0 - Coverage survey -- the hard gate for starting the project** (in progress, since 2026-09-17)

The direction follows what Xinwei set: do not compare speedups on individual models; instead **report coverage across a large number of messy real-world models**,
with the methodology modeled on Table 1 of the PyTorch 2 paper (ASPLOS'24).

The environment is ready: the container has torch `2.15.0a0+git71b3251` and torchvision `0.30.0a0` built from source
(self-building is required, because the partition **reason** strings only exist on main), a list of 131 models,
and everything runs under fake tensors with zero tensor memory. Details are in `SETUP.md` and `../../survey/README.md`.

Two figures to produce:

1. **Partition distribution**: for each of the three suites, how many models are full-graph cudagraphable / split into 2~9 segments / >=10 segments / cudagraphs abandoned for the whole graph
2. **Reason breakdown**: which rule the splits come from (`unbacked_binding` / `non_gpu_ops` / `device_copy` /
   `cudagraph_unsafe_custom_op` / ...)

Both configurations must be run, because they answer different questions: under PyTorch's out-of-the-box configuration, data dependence causes Dynamo graph breaks
and Inductor never sees it at all; only after enabling capture can you see how many segments the graph is really split into. Looking at only one side leads to the wrong conclusion.

> **Gate**: if the vast majority of real models can already be cudagraphed as a full graph, this project is not needed.
> Conversely, if "a single data-dependent op breaks the graph into seven pieces" is common, Figure 1 stands.

**P0' (optional) - Target-workload profiling** -- reserved for the P4 performance comparison, not a gate for starting the project
- PyG/DGL neighbor-sampled GNN training, MD with TorchMD-Net / MACE / NequIP, TorchSparse point clouds, TorchRec jagged
- Measure the GPU idle fraction, the per-step shape change rate, and the number of recaptures under `reduce-overhead`
- Measure the waste of their hand-written padding: the fraction of placeholder neighbor pairs in TorchMD-Net, the FLOPs spent on zero padding in TorchSparse

**P1 (reordered after the survey data came in) - Shape-driven first, data-dependent later**

The survey measured a **91 vs 2** split (`_purity2.py`):

| Category | Node count in one detection model | Reads the GPU? | Difficulty |
|---|---|---|---|
| **Shape-driven** CPU computation (the anchor-generation kind) | 91 | **0 read the GPU** | Pure functions; the planner evaluates the symbolic expressions |
| **Value-driven** CPU computation (the filter-boxes-by-score kind) | 2 | **All read the GPU** | Must wait for the device to finish; the hard part |

The original P1 went straight at data-dependent output size; it now looks like **the order was backwards**.
Most host involvement is not caused by data dependence but by **shapes being computed on the CPU**,
and that category does not read the GPU at all, so moving it over is a pure engineering problem.

- **P1a - Shape-driven planner**: use `ssd300_vgg16` as the target, and translate those 91 nodes
  (`repeat` tiling anchors, `add` adding offsets, `clamp` clipping to boundaries, `cat` concatenating the levels)
  into one planner kernel that computes on the device and writes into the arena, with downstream nodes reading it directly.
  This chain **has already been verified not to read any GPU buffer**; there is no "must wait for the device" dependency.
  > Gate: the SSD300 forward goes from 9 segments to 1~2 segments; correct across input sizes; no D2H sync.

- **P1b - Value-driven mechanism**: then take on data-dependent output size
  (radius neighbor list -> scatter -> segment reduce, or directly use the `extra:nms` / `extra:sparse` probes).
  The planner kernel reads sizes from device memory, computes arena offsets, and patches all nodes.
  > Gate: correct across inputs; **no D2H sync anywhere**; beats padding-to-max and per-shape recapture.

The advantage of this ordering is that P1a can first get the planner kernel, arena and node-patching mechanism running and validated,
without having to face the "the size is only known after the device computes it" problem at the same time. P1b then only swaps in a different size source on a mechanism that already works.

**P2 (8 weeks) - Inductor integration -- the technical core**
- **Carry unbacked SymInt all the way through to the graph node**. This is the real hard part, and PyTorch itself is still fixing it (those 11 fixes in 2026-07, bug #172728). Build on their ShapeEnv work; the CUDA graph part is something nobody has done
- Record the Triton node parameter layout and devNode handles; codegen the planner kernel from Inductor's sympy expressions
- **Device-side arena sub-allocator**: when sizes have no static upper bound, a max-shape plan is either impossible or hugely wasteful. The planner must actually compute the layout. This is upgraded from "optional in v2" to core
- A bail-out path for sizes that exceed the arena

**P3 (4 weeks) - Coverage and correctness**: training (autograd / RNG / collective), several workload families running end to end, verify-mode cross-checking
**P4 (4 weeks) - Performance on par with hand-written code**: match or beat hand-written baselines such as TorchMD-Net static-shape mode and TorchSparse
**P5 (4 weeks) - Evaluation and writing**

## 11. Recommendation

**Do it. But the target workload must be non-LLM dynamic models, not variable-length SFT.**

One-line pitch: **any dynamic model gets CUDA graphs just by compiling it** -- including the data-dependent output sizes that PyTorch gives up on outright today.

The three legs that hold up:
1. Four unrelated domains independently hand-wrote the same pad-to-max hack, which indicates a missing layer of abstraction
2. For these workloads the CUDA graph benefit today is **0** (PyG officially recommends turning it off), not a marginal improvement
3. Under data-dependent sizes, **a host-side approach is unworkable in principle**; it has to be device-side

**The biggest technical risk is not in CUDA graphs but in unbacked SymInt.** Inductor must carry data-dependent sizes all the way to the graph node without specializing and without graph breaks. PyTorch itself only fixed 11 places in 2026-07, and bug #172728 is closed. The good news is that this means we can build on their progress, and the CUDA graph part really is something nobody has done.

**Suggested first steps (three items, each on the order of a day)**:

0. **The cheapest and most valuable one**: run the 188 models from the PyTorch 2 paper (TorchBench + HuggingFace + TIMM) with `mode="reduce-overhead"` and measure **the fraction that gets a full cudagraph, the number of graph fragments, and the number of recaptures**. Because the fallback is silent, nobody has this number today. It is at the same time Figure 1, the gate, and the infrastructure needed for debugging later
1. **Serving side**: start a vLLM and measure the graph memory and capture time curves as `--cuda-graph-max-bs` goes from small to large, then measure the overhead at each attention boundary in piecewise mode. The numbers on this line are the most solid, and it is a domain Xinwei already knows well
2. **Non-LLM side**: run nsys once each on PyG neighbor-sampled GNN training and TorchMD-Net, and measure the GPU idle fraction and the per-step shape change rate

If either one holds, the project holds. If both hold, "one mechanism, two very different scenarios" is itself a good paper structure.
